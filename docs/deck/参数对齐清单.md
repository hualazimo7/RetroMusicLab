> 现状：`proto-aura.html` 里 7 组常量都是**按截图目测 + 反复调**出来的，不是参考实现的真实值。
> 目标：用这里的清单把它们换成真实值，一次对齐，不用再猜。

## 0. 先看是什么栈

这决定哪些值能直接读到、哪些只能靠猜。

| 看到什么 | 说明 | 取参难度 |
|---|---|---|
| `app.asar` / `resources/app/` / 成堆 `.js` `.css` | Electron 或 Web 栈 | **最简单**，值直接可读 |
| `*.qml` / `*.ui` | Qt | 较易，QML 里常直接写数字 |
| `flutter_assets` / `libapp.so` | Flutter | 中等，值在 asset 与常量池 |
| `*.pyc` / `__pycache__` | PyInstaller / Python | 中等，值在 pyc 常量里 |
| `.dll` / 汇编 / IL | 原生程序 | 只能取字符串与常量，重点翻资源文件 |

先跑一遍扫描器，它会自己判断哪些类别扫到了、哪些没扫到：

```bat
py -3.14 docs\deck\tools\scan_ref.py "D:\path\to\extracted" --out docs\deck\params.json
```

末尾的 `[!] not found:` 就是还需要手工翻的部分。

## 1. 七组待对齐常量

每项都写了「在参考代码里可能叫什么」和「对应 params.json 的哪个字段」。
**找到就填，找不到留 `null`，不要按截图猜** —— 猜的数值现在已经在原型里了，再猜一遍没有意义。

### ① 点阵的列数与行数 → `dots.cols` / `dots.rows`

现在估 **22 × 14**。这个数字决定整块面板的密度，差 2 列观感就不对。

搜：`COLS` `COLUMNS` `BARS` `barCount` `DOT_COLS` `numBars` / `ROWS` `LEVELS` `steps`
也可能不叫名字，而是硬编码在循环里（`i < 24`）或用数组字面量长度体现。

### ② 三段色分界 → `dots.bandEdge`

现在估 **0.235 / 0.60**（归一化高度）。**这条最值钱** —— 它决定「多高算中段、多高才露顶段色」，我目测调了四轮仍不准。

搜：`band` `threshold` `tier` `split` `BAND_EDGE`
更可能藏在渐变里：`linear-gradient(to top, c1 0%, c1 24%, c2 24%, ...)` —— 里面那几个百分比就是分界，直接取。
注意如果分界写的是 `px` 而不是 `%`，记下来，换算要用点阵区总高。

### ③ 四档透光强度 → `glowLevels` / `ringOpacity`

现在估 `{off:0, low:.3, mid:.58, high:.96}` 与 `{off:.36, low:.62, mid:.88, high:1}`。

**要绝对值，不要相对关系** —— 相对关系我自己能推，绝对值推不出来（尤其 low 档到底多暗）。

### ④ 光晕 blur 与扩散 → `halo`

现在估 `blur(24px)`、`inset: -15px`。

若是多层 `box-shadow: 0 0 12px c, 0 0 32px c, 0 0 64px c`，**整条记下来**，层数本身就是信息（我们目前只用一层 filter）。

### ⑤ 呼吸 / 环绕周期 → `motion.breatheSec` / `motion.spinSec`

现在估 3.8s / 13s。`animation: name 4s ease-in-out infinite` 里的 `4s` 就是。

### ⑥ 律动映射 → `motion.pulseFormula` / `motion.pulseThrottleFrames`

现在估 `--glow = base * (0.46 + rms * 1.05)`。

重点看三件事：**用哪个数据源**（时域 RMS 还是频域均值）、**怎么归一化**、**有没有衰减/平滑**。
另外看它是不是每帧都写 CSS 变量 —— 我们目前每 3 帧写一次，如果对方每帧写也没掉帧，说明我们的保守可以放开。

### ⑦ 材质噪声 → `material`

现在估 `baseFrequency='.82'`、`numOctaves='3'`、`opacity=.5`。
也可能根本不是 SVG 噪声，而是位图贴图或 `backdrop-filter` —— 如果是，`material.type` 记下，我们把 SVG 那套换掉能省不少。

## 2. 顺手值得记的（`drawing` / `unmapped`）

这几条不改变数值，但可能直接推翻我们的实现选择：

| 项 | 为什么重要 |
|---|---|
| **点阵怎么画的** | 逐点 `arc` 还是「画柱 + mask 打点」？后者省一半开销，观感差一档 |
| **辉光怎么做的** | `shadowBlur` / 预生成贴图 / CSS filter —— 这条决定性能上限。我们用贴图，若对方用 `shadowBlur` 也能跑，说明我们的性能预算太保守 |
| **熄灭点画不画** | 我们画（中性灰不透明）。对方若不画，说明深底足够暗，灰网格可以省掉 |
| **切档位有没有过渡** | 硬切还是 200ms 淡入？影响 `levelTransitionMs` |
| **颜色表** | 4 套灯光的三段色 + 边框色、7 种氛围色的 hex，全部记下来，纯数据最有价值 |
| **点阵区宽高比** | 有它 + 点直径 + 间距，比例能完全对齐 |
| **prefers-reduced-motion** | 有没有处理 |

## 3. 红线

1. **不把反编译代码放进仓库**。`params.json` 只填数字、hex、一句话描述。`scan_ref.py` 已经做了值截断（48 字符），不会带出函数体。
2. **不搬素材**（图片、字体、图标、音频）。颜色值不算素材。
3. **反编译产物不上传云端**（包括发给我）。填完的 `params.json` 几十行数字就够。

如果某个值只能靠贴一段代码才说得清 —— 那就**用一句话描述它的做法**（填进 `unmapped`），实现由我重写。结构本来就是独立设计的，缺的只是数值。
