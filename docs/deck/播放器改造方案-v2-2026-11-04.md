## 0. 这份文档改了什么

原方案是「先定双风格骨架，再插 DSP，最后调参数」。两份逆向之后，有三个事实改变了排序依据：

1. **Deck 参考对象（Re:Play）的核心参数是实测确证的**：卡带几何、走带物理、音频链、LED 频谱，全部有具体数值；
2. **极光参考对象（AURORA Player）的 7 组外观常量一个都没拿到**：Nuitka 编译后无法从静态产物提取，只能靠原型目测；
3. **两个参考产品的功能范围都比我们大一个数量级**（Re:Play 有 80 个 IPC、云同步、商城、电台；AURORA 有整套 `brain_*` 推荐体系），而我们的范围已经收窄。

所以 v2 的核心调整是：**Deck 先做、极光后做；音频内核先于界面；极光的参数对齐从「前置条件」降级为「迭代项」。**

## 2. 六个判断修正

### 修正 1：Deck 先于极光（原为 P1a / P1b 并列）

- Deck 的关键参数全部可验证（半径曲线、角速度、翻面时长、LED 映射都能写成单测）；
- 极光的关键参数（点阵行列、三段色分界、透光四档、辉光 blur、呼吸/环绕周期、律动公式、材质噪声）**全部未确证**；
- 先做 Deck，可以在不依赖「猜数值」的情况下把骨架、契约、音频链全部跑通；极光到时只需换渲染器，不再动内核。

> 如果整体工期被压缩，极光可以作为 P2 可选交付，Deck 单独上线不影响产品完整性。

### 修正 2：Deck 的频谱改成「10 段 LED」，极光保留「22×14 点阵」

原 `实现路径.md` 给 Deck 设计的是 **15 列 LED**，`点阵与辉光-动效方案.md` 给极光是 **22 列 × 14 行点阵**。逆向结果支持把两者明确拆开：

| 皮肤 | 渲染器 | 分频 | 映射 |
|---|---|---|---|
| Deck | `led10` | 10 段固定倍频程：63 / 125 / 250 / 500 / 1K / 2K / 4K / 8K / 12K / 16K，段边界取相邻中心频率的**几何平均** | 每段取区间内 FFT bin 最大值，`min(10, max/25.5)` → 10 档，正好 10 颗 LED |
| 极光 | `dots` | 22 列，`t^1.85` 对数取样（沿用原型） | 14 行高度，按行分三段色 |

10 段是「硬件 LED 频谱」的标准做法，22 列是「点阵屏」的做法，两者不是替代关系，是两个渲染器。

### 修正 3：卷盘数学换掉（原 `实现路径.md` §6 线性插值作废）

| 项 | 原方案 | v2（Re:Play 实测） |
|---|---|---|
| 半径 | `rMin + (rMax-rMin)*(1-p)`，rMin .55 / rMax 1.0 | 左 `sqrt(1-0.72p)`、右 `sqrt(0.28+0.72p)` |
| 角速度 | 写死 `v≈5.0` 归一化线速度 | `ω = v / h`，v = 1.5（播放）/ 10（快进）/ -10（倒带），B 面取反 |
| 平滑 | 未定义 | 一阶平滑，时间常数 9（约 111ms） |
| 重绘 | 每帧 | 16ms 节流 + 「角度签名」变化才重绘 |

平方根模型来自「磁带长度 ∝ 半径²、恒带速下半径随剩余长度开方」，物理正确；线性插值在 p≈0.7 之后会明显偏快，肉眼能看出来。

### 修正 4：VU 保留真实 RMS，但降为「轻量真实」

- 参考产品的主力界面 VU **基本是装饰**（早期 `Math.random()`，现在只在电源开关时摆一下）；
- 原方案 `实现路径.md` §6 要求「真实 RMS + 峰值保持 + 300ms 回落」，方向对，但成本可以降；
- v2：**保留真实 RMS**（不做假表），但只保留「起针立即、落针 300ms 缓释」两个行为，不做峰值保持的独立指针、不做刻度校准动画；VU 只在 `播放中 || 指针未落稳` 时更新。

### 修正 5：`fftSize` 提到 8192，`smoothing` 保持 0.78

现状实测：`viz.js` 是 `fftSize 2048`、`smoothing 0.78`。Re:Play 是 `8192` / `0.78` —— **smoothing 已经一致，fftSize 差 4 倍**。

- 2048 在 44.1k 下每 bin ≈ 21.5Hz，63Hz 段只有 1–2 个 bin，10 段低频会抖；
- 8192 每 bin ≈ 5.4Hz，63/125/250 三段才站得住；
- 代价：FFT 计算量 ×4、`freqData` 从 1KB 涨到 4KB。只建一个 analyser、只读需要的 bin，实测可接受（S0 验证 60fps）。

### 修正 6：磁带染色降级为 P2 可选，不进 MVP

Re:Play 的「磁带味」= 高频搁架 **4500Hz −2dB** + 低通 **15500Hz Q −3.01** + **−54dBFS** 带限噪声（HP 1450 / LP 10k），过渡 0.08s。

这套参数很适合做 `warm` 预设的增强，但它是**新的参数类型**（shelf / lpf / noise），会打破 A1 已验证的「只叠加 bands」规则。v2 的处理：

- MVP 只做 EQ 曲线（`presetBands + userBands`），不改；
- P2 可选：把 `tape` 做成**预设包**（bands + shelf + lpf + noise），`Core.tone.preset` 从「曲线」升级为「曲线 + 轻染色参数」，但仍然是预设而不是开关，不破坏「开关归用户」的边界；
- 噪声默认关（chiptune 本身干净，底噪可能反而脏），只在磁带预设下开。

## 3. 修订后的架构

```
Core（唯一内核）
├─ state   播放/曲目/进度/皮肤/音量
├─ audio   单例 <audio>（只读引用）
├─ viz     AnalyserNode（fftSize 8192, smoothing 0.78）+ 渲染器注册
└─ tone    { preset, bands[9], flags{master,space,dyn,loud}, volume }
           实际值 = clamp(presetBands + userBands, -6, +6)

渲染器（可替换，皮肤只能选，不能自己接图）
├─ bars   现有 48 柱 + 波形（保留，回滚用）
├─ led10  Deck：10 段 × 10 颗，橙 #e8973d / 红 #de4b2f
└─ dots   极光：22 × 14 点阵，按行三段色

皮肤（只读状态、只调 Core）
├─ skin_deck    卡带 / 走带 / LED / VU / 两颗旋钮
└─ skin_aurora  程序化封面 / 点阵 / 辉光 / 音色曲线 / 9 段 EQ

音频图（在现有链上增补，不重建）
src → inGain → lowshelf(220) → highshelf(3500) → EQ×9 → tone → comp → limit → outGain → destination
                                                             └→ analyser（并联 tap，取在 outGain 之前）
```

四条不变量不变（皮肤不碰音频图 / 不建 DSP 节点 / 不直接写 `param.value` / 不写 localStorage、不发请求）。

## 9. 建议的第一个动作

**先做 S0 的独立 HTML demo，不进产品。**

理由：它零风险（不碰 `web_ui/` 任何文件）、当天能出结果、且同时验证三件最容易返工的事——卷盘半径曲线、`v/h` 角速度、10 段 LED 映射。如果这三样在 demo 里看着不对，改 demo 的代价是改产品的十分之一。

demo 通过后，S1 的音频内核和 S3 的皮肤就有了一份「已经被眼睛和单测确认过」的参数基线，不必一边写产品一边猜参数。
