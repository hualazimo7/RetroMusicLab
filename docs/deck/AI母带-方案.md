# AI 母带：音源匹配音色 —— 实现方案

> 状态：方案，未动产品代码。
> 定位：极光风格的核心功能。职责**只有一件事** —— 播放什么音源，就匹配什么音色。
> 不是替用户做决定，而是给用户一个正确的起点。
>
> 依赖：[`音色引擎-分析.md`](音色引擎-分析.md) 的 DSP 链（本文只解决「参数从哪来」，
> 不重复「节点怎么接」）。

---

## 0. 职责边界（这是本文最重要的一节）

用户已经明确两条，直接决定架构：

1. **AI 只匹配音色** —— 不碰别的，不做「全都帮你调好」；
2. **四个开关和 9 段 EQ 归用户** —— 空间音效、动态增强、响度平衡、AI 母带可分别独立开关，
   9 段 EQ 可手动打开、手动调，**手动调节永久保留，不被 AI 覆盖**。

于是分工是一张这样的表，**没有一格重叠**：

| 模块 | 谁决定 | AI 能不能改 |
|---|---|---|
| AI 母带（音色预设 + 基础 EQ 曲线） | **AI 按音源分析** | 是（这是它唯一的职责） |
| 空间音效 开/关 | 用户 | **不能** |
| 动态增强 开/关 | 用户 | **不能** |
| 响度平衡 开/关 | 用户 | **不能** |
| 9 段 EQ 手动值 | 用户 | **不能** |
| 音量 | 用户 | **不能** |

**「不按自己的喜好」在这里的含义**：AI 不做用户画像、不学听歌习惯、不因为「你上次喜欢低频重」
就给你加低频。它只看**这一首曲子的客观频谱**。换一首完全不同机种的曲子，判定就跟着变。

**AI 唯一能主动做的事**：给出一套音色曲线作为起点。用户可以关掉它，也可以在上面继续调。

## 1. 不做的功能（不要放进后续分期）

极光只做播放器功能。以下一律不做：

| 不做 | 原因 |
|---|---|
| 电台 / 收音机 | 没有流媒体，试听对象是本地转换产物 |
| 歌词（含「元数据跑马灯」替代方案） | 用户明确不要，原方案 §3 的跑马灯一并撤销 |
| AI 懂你 / 推荐 / 歌单 / 用户画像 | **与「按音源匹配」相反**，做了就变成猜喜好 |
| 账户 / 积分 / 商店 / 创作者中心 | 对方商业系统，本项目是离线工具 |

留下六件：**大封面、点阵频谱、音质信息条、传输控制、AI 母带、手动控制区（三开关 + 9 段 EQ）**。

## 2. 关键设计：AI 曲线与手动 EQ **相加**，不互相覆盖

这是整份方案里唯一需要仔细想的结构问题。

如果 AI 直接把值写进 9 段 EQ 的滑块位置，用户一调就会和 AI 打架：
下一首歌 AI 又覆盖回去，用户调的东西没了 —— 这正是「手动调节保留不了」的典型死法。

**解法：把「AI 给的」和「用户调的」拆成两个数组，最终值相加。**

```
实际应用 = clamp(presetBands[i] + userBands[i], -6, +6)
           ↑ AI 按音源算          ↑ 用户手动，默认全 0
```

| 场景 | `presetBands` | `userBands` | 听到的 |
|---|---|---|---|
| AI 开，用户没动 | 芯片曲线 | 全 0 | 纯 AI 曲线 |
| AI 开，用户加了 +2dB 低频 | 芯片曲线 | 第 0 段 +2 | AI 曲线 + 用户修饰，**叠加** |
| AI 关，用户自己调 | 全 0 | 用户值 | 纯手动 EQ，就是个普通均衡器 |
| 换到下一首，用户加过低频 | 新曲曲线 | 第 0 段仍 +2 | 用户偏好**跟着走**，AI 底换成新曲的 |

四行都在同一套规则下产生，没有特例分支。这才是「保留手动调节」的正确实现。

### 为什么要 clamp 到 ±6dB

`presetBands` 上限 ±4、`userBands` 上限 ±6，相加最坏到 ±10。
在芯片音乐上 +10dB 的低频会直接糊掉方波，所以最终值必须压回 ±6。

### UI 怎么表达「两层」

滑块位置 = 实际值（用户看到的），但滑块后面画一条**淡色轮廓线** = `presetBands`。
用户一眼能看出「这段是 AI 给我的，我往上推了 2dB」。给一个「清除手动调节」按钮只清 `userBands`。

## 3. 分析放在 Python 侧，不放前端

| 理由 | 说明 |
|---|---|
| **算得准** | 前端只有 `getByteFrequencyData()`，8 位量化 + 对数刻度，算不出「高频滚降点」 |
| **不占内存** | `decodeAudioData` 会把整个文件解进内存，3 分钟立体声 float32 ≈ 63MB |
| **可缓存** | 同一文件只算一次；前端每次播放都要重算 |
| **可测试** | 纯函数 `analyze(path) -> dict`，能用合成信号写断言（§8） |

依赖已齐：`numpy==2.5.4` 在 `requirements.txt` 第 10 行，`build_web_pyi.py` 的 `COLLECT_ALL`
也保留 numpy。**不新增任何第三方包。**

### 接口契约

```
GET /api/tone?id=<output id>
→ 200 {
    ok: true,
    id: 12,
    cached: false,
    feat: { centroid, lowRatio, rolloff, crest, rmsDb, clip, sr, bits, secs },
    tone: {
      preset: "chip",
      presetBands: [0,0,1,1,0,0,0,0,0],
      reason: ["低频偏重", "高频止于 11.2kHz", "确认为芯片音源"]
    }
  }
```

三点约束：

- **不返回任何开关状态**。`flags` 字段刻意不设 —— 一旦返回，就有人会去自动打开它。
- 路径校验照抄 `_audio()`（`server.py:1629`）：只放行 `state.find_output(oid)` 登记过的文件，
  不接受任意路径，否则是任意文件读取漏洞。
- 只读，不改状态，不碰转换链路。失败/静音/太短 → `ok:false`，前端直通，不弹窗。

## 4. 特征提取

采样策略：取 **10% / 50% / 85% 三处各 5 秒**。芯片音乐常带长前奏或循环尾，只取开头会误判；
WAV 可 `seek`，读三段仍很快。文件短于 10 秒就退化为整段。

```python
import wave, numpy as np

_WIN_SECS, _POSE = 5.0, (0.10, 0.50, 0.85)

def _mono(path):
    """读三段并混单声道。位深/声道以文件头为准，不假设。"""
    with wave.open(path, "rb") as w:
        nch, sw, sr, n = w.getnchannels(), w.getsampwidth(), w.getframerate(), w.getnframes()
        dtype = {1: np.uint8, 2: np.int16, 4: np.int32}[sw]
        win  = int(sr * _WIN_SECS)
        spans = ([(0, n)] if n <= win * 2 else [(int(n * p), win) for p in _POSE])
        chunks = []
        for off, cnt in spans:
            w.setpos(off)
            a = np.frombuffer(w.readframes(min(cnt, n - off)), dtype=dtype)
            if sw == 1:
                a = (a.astype(np.float32) - 128.0) / 128.0
            else:
                a = a.astype(np.float32) / float(2 ** (8 * sw - 1))
            if nch > 1:
                a = a.reshape(-1, nch).mean(axis=1)
            chunks.append(a)
    return np.concatenate(chunks), sr, sw * 8, n / float(sr)
```

```python
def _feats(mono, sr):
    n_fft, hop = 2048, 1024
    if mono.size < n_fft:
        mono = np.pad(mono, (0, n_fft - mono.size))

    rms  = float(np.sqrt(np.mean(mono ** 2)) + 1e-12)
    peak = float(np.max(np.abs(mono)) + 1e-12)

    frames = np.lib.stride_tricks.sliding_window_view(mono, n_fft)[::hop]
    mag    = np.abs(np.fft.rfft(frames * np.hanning(n_fft), axis=1)).mean(axis=0)
    freqs  = np.fft.rfftfreq(n_fft, 1.0 / sr)
    power  = mag ** 2
    total  = float(power.sum()) + 1e-12

    cum = np.cumsum(power)
    return {
        "centroid": float((freqs * power).sum() / total),      # 频谱重心 → 亮度
        "lowRatio": float(power[freqs < 200].sum() / total),   # 低频占比
        "rolloff":  float(freqs[np.searchsorted(cum, cum[-1] * 0.95)]),  # 95% 能量点
        "crest":    float(20 * np.log10(peak / rms)),          # 峰值因数
        "rmsDb":    float(20 * np.log10(rms)),
        "clip":     float(np.mean(np.abs(mono) > 0.999)),
    }
```

**6 个特征里，只有前 3 个 + `clip` 参与音色判定**。`crest` / `rmsDb` 仍然算，
因为它们要显示在面板上，且用户打开「响度平衡」时后端不需要再算一遍（§6）。

## 5. 音色映射规则

只决定 `preset` 与 `presetBands`，不决定任何开关。

### 5.1 选哪一档预设

| 条件 | 判定 | 预设 |
|---|---|---|
| `rolloff < 12000` 且 `lowRatio` 正常 | 确认是芯片音源 | `chip` |
| `lowRatio < 0.12` | 低频偏薄 | `warm` |
| `crest > 16` 且 `rolloff > 14000` | 动态大且有真实高频 | `space` |
| 分析失败 / 用户关了 AI | —— | `bypass`（空曲线） |

`vocal` / `music` 这类按人声分的预设**不要** —— 芯片音乐没有「人声轨」这个概念，
留着只会让用户困惑。

### 5.2 曲线怎么给

| 条件 | 动作 |
|---|---|
| `lowRatio > 0.35` | 第 0/1 段 **−2dB**（低频过重，收） |
| `lowRatio < 0.12` | 第 0/1 段 **+2dB**（偏薄，补） |
| `centroid < 900` | 第 4/5 段 **+2dB**（整体偏暗） |
| `centroid > 3000` | 3kHz 附近 **−1.5dB**（偏刺） |
| `rolloff < 12000` | 第 8 段（16k）**固定 0** —— 开了只是放大重采样噪声 |
| `clip > 0.001` | 不调 EQ，只在 `reason` 里标注「已有削波」 |

`presetBands` 上限 ±4，比手动上限小 —— 这是有意的：**AI 只给起点，激进调整留给用户**。

### 5.3 「为什么不给 AI 加动态和响度」

因为用户明确说「音色跟着音源走」，而动态/响度是另外两个独立开关。
如果 AI 在后台顺手把压缩比也改了，用户关掉「动态增强」时会发现「怎么还有压缩」，
这种「看不见的手」是最容易被投诉的设计。

**但**：用户**主动打开**「响度平衡」时，增益值可以用 `feat.rmsDb` 算（见 §6），
因为那时候是用户要它工作的，不是 AI 偷偷做的。这条线要划清：

> 开关归用户；开关打开后，参数值可以来自当前曲目的分析。AI 从不主动拨开关。

## 6. 三个手动开关各自怎么工作

这三个都独立于 AI，但既然分析了音源，参数可以复用（不用二次分析）。

### 6.1 空间音效

`ConvolverNode` + 程序生成 IR（0 位图，1.6s 指数衰减噪声，见 `音色引擎-分析.md` §4.5）。
开关状态由用户保存，**不随曲目变**。混响量固定，不自动调 —— 混响量随曲目变会让人觉得
「同一首歌有时湿有时干」。

### 6.2 动态增强

`DynamicsCompressorNode`，参数固定（threshold −24 / ratio 3 / knee 6 / release 0.25）。
不按曲目变，理由同上：压缩量变化比压缩本身更容易被听出来。

例外：`feat.clip > 0.001`（已削波）时，把阈值降到 −26 —— 这不是「音色」，是保护，
属于安全行为。要在 UI 上标一句「检测到削波，已加强限幅」。

### 6.3 响度平衡

开关打开后按曲目算增益，**这是唯一「参数随曲目变」的手动功能**：

```python
target_db = -16.0                                   # 试听一致性目标
gain_db   = max(-8.0, min(+8.0, target_db - rmsDb)) # 单曲最多补 8dB
```

±8dB 上限是必要的：超过 8dB 会把安静段落也抬起来，动态感消失。
宁可「这首稍小」，不要「全都一样响」。

**这一项收益最直接**：同一批转换产物里，不同机种输出电平能差 6–12dB，
现在用户每换一首都要拧一次音量。

## 7. 决策时机与防跳变

### 7.1 每首曲子只决策一次

不在播放过程中重算。芯片音乐常带明显段落反差（快段/慢段/空拍），
实时重算会让曲线在两段之间来回游移，听感是「音染在呼吸」，比不处理更难听。

时机：`playOutput()` 里 `audio.src = ...` 之后立刻 `fetch('/api/tone?id=')`（约 30–60ms）。
**播放不等它** —— 先直通出声，结果到了再 300ms 渐变过去。

### 7.2 缓存

```js
// localStorage: rml-tone-cache → { "<id>": {size, mtime, tone} }
// key 带 size+mtime，文件重转后自动失效；LRU 200 条
```

命中直接应用，不发请求。

### 7.3 过渡

所有参数 `setTargetAtTime(v, ctx.currentTime, 0.08)`，约 300ms 完成。
短于 300ms 有「音色突然塌陷」感，长于 500ms 用户以为没生效。

### 7.4 用户动过之后

只要用户碰了任一 EQ 滑块，`userBands` 就有值，**永久保留**（存 `localStorage`）。
AI 换曲只改 `presetBands`，两者相加 —— 用户的调节不会丢，也不会跨曲叠加错乱。

关掉「AI 母带」开关 → `presetBands` 归零 → 只剩用户自己的 EQ。
**这是「我不想被 AI 管」的出口**，必须有。

## 8. 可解释性：面板要说「为什么这么选」

```
低频偏重 · 高频止于 11.2kHz · 确认为芯片音源  →  芯片增强（16k 段保持 0）
```

来自 `tone.reason`，是分析结果的原话，不是营销文案。三个作用：

1. 用户知道不是随机选的 —— 否则「AI 母带」和「随机预设」在感知上没区别；
2. 出问题能归因 —— 用户说「这首闷」，从这行能看出是判定错还是曲线不合适；
3. 验收有凭据 —— 截图里能看到具体数值。

对方那种「学习已暂停，仍载有已给基准推荐」的文案不要学，说不清在做什么。

## 9. 与导出的关系

处理全在 Web Audio 图上，导出走 Python 侧（`cd_audio.py` / `dl_convert.py` / `wavmerge.py`），
两者不共享代码路径。

> **AI 母带与三个开关只影响试听，不影响导出的 WAV。**

要同时写在面板注释和 README 里。否则用户拿着「试听很饱满」的预期去播导出文件，
就是一个必然的售后问题。

不建议让导出也走同一套 DSP：得在 `cd_audio.py` 里用 numpy 复刻压缩器、限幅器、卷积，
一致性风险极大，而且「试听好听、导出不一样」比「不处理」更难解释。

## 10. 验收

### 10.1 后端单测（`_smoke_tone.py`，纯函数）

| 信号 | 构造 | 期望 |
|---|---|---|
| 纯方波 440Hz | `sign(round(sin))` | `rolloff` 高、`crest ≈ 3dB` → `chip` |
| 白噪声 | `rng.normal` | `centroid > 3000` → 高频段有负值 |
| 低频正弦 60Hz | `sin(2π·60t)` | `lowRatio > 0.9` → 第 0/1 段 −2 |
| 静音 | 全 0 | `ok:false`，不抛异常 |

另加：同一文件算两次结果完全一致（确定性）；`bits/sr` 等于文件头值，不是写死 44100。

### 10.2 叠加规则单测（前端，纯逻辑）

这条比后端更重要，因为手动保留全靠它：

| `presetBands` | `userBands` | 期望实际值 |
|---|---|---|
| `[0,0,1,1,0,...]` | 全 0 | 等于 preset |
| `[0,0,1,1,0,...]` | `[2,0,0,0,...]` | `[2,0,1,1,...]` |
| 全 0（AI 关） | `[2,0,0,0,...]` | `[2,0,0,0,...]` |
| `[4,0,...]` | `[6,0,...]` | **clamp 到 `[6,...]`**，不是 10 |

### 10.3 端到端

```
1. 转两首已知曲目（8bit 方波重 / PCE 干净）
2. GET /api/tone?id=0 与 id=1 → 断言 preset 不同
3. 断言 tone 里没有 flags 字段（防回归：AI 不许管开关）
4. 第二次请求 cached:true 且 < 5ms
```

### 10.4 前端

| 检查 | 方式 |
|---|---|
| 失败降级 | `/api/tone` 返回 500 时仍能播放（直通），不弹错 |
| 无跳变 | 连切 5 首，`ctx` 不重建、无爆音 |
| **手动保留** | 拖一次 EQ → 切 3 首 → 断言 `userBands` 仍在、听感有修饰 |
| AI 关闭 | 关开关后 `presetBands` 全 0，曲线回到用户值 |

## 11. 名字与边界（说清不夸大）

用户定名「AI 母带」，功能确实是「根据音源智能匹配音色」，这个名字不虚。要守住的是**不夸大**：

| 可以说 | 不能说 |
|---|---|
| 按音源频谱自动匹配音色 | 「学习你的听歌习惯」 |
| 本地计算，音频不上传 | 「模型训练」 |
| 每首曲子独立判定 | 「越用越懂你」 |

技术上它是规则引擎：4 个特征 → 阈值映射 → 1 组曲线。**好处是确定性**：
同一个文件永远得到同一套参数，能复现、能回归测试。

真上神经网络（打包 onnx 几十 MB）在这个工具里没有收益 —— 目标不是猜喜好，
是让不同机种的输出听起来一致。这件事规则引擎做得比小模型好，而且用户能看懂为什么。

以后要升级，正确方向不是加模型，而是**加特征**（比如按 1/3 倍频程做 12 段目标曲线匹配），
那是同一套架构里加表，不是换技术栈。

## 12. 分期

| 期 | 内容 | 独立验收 | 风险 |
|---|---|---|---|
| **A0** | `/api/tone` + 特征提取 + 缓存，前端只**显示数值**（不改音色） | 4 个合成信号单测全绿；两首曲子数值合理 | 极低（纯只读） |
| **A1** | 模型：`presetBands` + `userBands` 相加 + clamp，9 段 EQ 可手动 | §10.2 四行叠加单测全过 | 低（纯逻辑） |
| **A2** | AI 应用（预设匹配）+ 平滑过渡 + 缓存 LRU | 两首曲子听感方向正确 | 中：阈值调不准 |
| **A3** | 三个开关独立 + 响度平衡用 `rmsDb` + 削波保护 | 各开关互不影响；关掉 AI 仍有手动 EQ | 中 |
| **A4** | 面板「匹配依据」行 + 重新匹配按钮 + 失败降级 | 截图能看到理由；500 时不弹窗 | 低 |

**A0 与 A1 可以并行，且都不依赖 UI。** 建议先做这两期：
前者验「算得对不对」，后者验「叠加会不会打架」，两个问题都能客观断言。
「好不好听」留到 A2 靠人耳，混在一起做就会来回改。

## 13. 待决策

1. **`userBands` 是全局保留还是按曲目**：建议**全局**（它是用户偏好，不是单曲修饰）。
