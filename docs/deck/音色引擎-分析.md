# 极光的真正识别点：音色引擎 —— 实现路径分析

> 状态：分析，未动产品代码。
>
> 前提：用户指出「极光重点特征是根据音频生成音色」，而不是黑金封面 + 点阵频谱。
> 这条纠正同时**降低了** [`双风格-可行性分析.md`](双风格-可行性分析.md) 里三处「无数据源」的严重性，
> 也把工作量重心从「画界面」挪到「搭 DSP 链」。

---

## 0. 结论先行

1. 截图右栏那一堆控件，**本质是一条可切换的 Web Audio 处理链 + 一组预设参数**，不是六种独立技术。
2. 本项目现在是**零 DSP 直通**：`src → analyser → destination`，没有任何滤波、压缩、增益节点。
   所以这不是「改样式」，是「插链」，属于内核改造，两种皮肤都得等它。
3. 音色引擎必须放在**内核层**，不能放在皮肤里 —— 否则切皮肤音色就断，第二次踩 `viz.js:11-21` 那三个坑。
4. 「AI 母带」这个词有诚实性问题（§6）。本项目没有推理后端，做不到对方宣传的「学习曲库」。
   但有一件真能做的事：**测当前曲目的频谱重心和动态范围，自动选预设**。这是真测量，可验收。
5. 本项目素材是 chiptune，不是流行乐。把对方的 ±12dB 预设照搬过来会糊掉方波（§7）。
   预设要重做，不是翻译。

## 1. 截图右栏拆成 6 个模块

先把「看到的东西」和「要写的代码」对上，避免把 UI 分组当成技术分组。

| # | 截图里的模块 | 实际控件 | 对应的 Web Audio 手段 | 可行性 |
|---|---|---|---|---|
| 1 | 音色预设 | 直通 / 低音 / 人声 / 音乐 / 自定义 / 剪辑 EQ，6 格 | **就是 6 组 EQ 参数**，不是 6 套算法 | 可做，成本低 |
| 2 | 声景渲染 | 4 个开关：AI 母带 / 空间音效 / 动态增强 / 响度平衡 | 压缩器 + 卷积 + AGC + 限幅，各一个节点 | 可做，见 §4 |
| 3 | 当前状态文案 | 「当前：直通，未做任何染色」 | **建议照抄这个设计**：给「有没有染色」一个明确口径 | 可做，且应做 |
| 4 | 剪辑 EQ | 9 段 −12…+12dB | 9 个 `peaking` BiquadFilter 串联 | 可做，但见 §7 的段数建议 |
| 5 | 模拟 VU 表 + 音量 72% | 双表 + 滑杆 | VU 用 RMS，音量接管现有滑杆 | 可做，但**必须先解决双口径**（§5-2） |
| 6 | AI 母带 / 输出设备 | 按钮 + 「未检测到输出设备」 | 见 §6、§5-1 | 有条件可做 |

底部那行「WAV / 48 kHz / 16-bit / LOCAL」不是音色功能，是信息条 —— 本项目 `probe.py` 比它细，
但**采样率必须写 44100**（全库 `OUT_RATE = 44100`，`cd_audio.py:53`、`mod_audio.py:49` 等 8 处一致），
不能照抄截图里的 48 kHz。

## 2. 现状：一条链，零处理

```js
// web_ui/viz.js:161-168（原文）
const src = ctx.createMediaElementSource(audio);
const an  = ctx.createAnalyser();
src.connect(an);
an.connect(ctx.destination);   /* ← 不接这一步，声音就没了 */
```

三个已确认的事实：

| 事实 | 位置 | 对本次改造的含义 |
|---|---|---|
| 图上只有 3 个节点，无任何处理节点 | `viz.js:161-168` | 要加的全部是新增，不存在「改参数」的省事路径 |
| 音量走 `audio.volume = vol/100` | `app.js:927` | 一旦引入 GainNode 就有**两个音量**，必须统一（§5-2） |
| 只在 `playOutput()` 里 `ensure()` | `app.js:465-469` | 图的生命周期挂在播放动作上，切预设时图已存在，绝不能重建 |

`viz.js` 顶部注释（11-21 行）已经记过三条坑，其中第一条就是**构造函数只能调一次**。
本次改造的整个设计都要围着这条约束转。

## 3. 目标音频图

```
                                    ┌──────────────┐
 src ──► inGain ──► EQ(1..N) ──► tone ──► comp ──► limit ──► outGain ──► destination
 (media)  (前哨)      (Biquad)   (搁架)  (动态)  (软限幅)  (音量)      
                                        │
                                        └──► analyser（并联 tap，不串在主链上）
```

**四个设计决定，每个都有理由：**

| 决定 | 做法 | 为什么 |
|---|---|---|
| analyser **并联**而非串联 | `limit.connect(an)`，`limit.connect(outGain)` 两条同时接 | 串联也能工作（analyser 是 pass-through），但并联后将来加「前/后级切换显示」不用改图 |
| analyser 取在 **limit 之后、outGain 之前** | 见上图 | VU 反映真实峰值，且**不随音量旋钮变化** —— 录音室惯例，也是唯一能让 6 套主题下 VU 读数一致的口径 |
| `audio.volume` 钉死 1.0 | `audio.volume = 1`，音量交给 `outGain` | 消灭双口径（§5-2） |
| 所有节点**只建一次** | 参数变化只改 `param`，不 `disconnect` 主链 | `createMediaElementSource` 只能调一次（`viz.js:13`） |

只有一种情况需要改接线：**开关某个效果时**。这时用「干湿双路 + 交叉淡化」，而不是断链重接（§5-3）。

## 4. 六个模块的具体实现

### 4.1 音色预设 = 参数集，不是代码分支

```js
// 一组预设就是一个数组，切换 = 逐个 param 平滑过渡
const PRESETS = {
  bypass:  { eq: [0,0,0],        lowShelf: 0,   airShelf: 0,   comp: 0,   space: 0 },
  bass:    { eq: [0,0,0],        lowShelf: +5,  airShelf: 0,   comp: 0,   space: 0 },
  vocal:   { eq: [-2,+3,+1],     lowShelf: -3,  airShelf: +2,  comp: 0,   space: 0 },
  music:   { eq: [0,+1,+1],      lowShelf: +2,  airShelf: +1,  comp: 0.3, space: 0 },
  chip:    { eq: [0,+1,+2],      lowShelf: +1,  airShelf: +1,  comp: 0,   space: 0 },  // 本项目新增，§7
  custom:  null,                 // 用户动过滑杆就落到这里
};
```

**「自定义」是状态，不是预设。** 用户拖任一滑杆 → 当前预设名自动变 `custom`。
截图上第 5、6 格并列（自定义 / 剪辑 EQ），说明对方也是这个逻辑。

### 4.2 剪辑 EQ

`N` 个 `BiquadFilterNode({type:"peaking"})` 串联，频率对数等分：

```
f[i] = f0 * (f1/f0)^(i/(N-1))     f0 = 62Hz, f1 = 12kHz
Q    = 1.1（固定，别让用户调，一调就是无底洞）
gain = ±6dB（本项目上限，见 §7；对方是 ±12）
```

### 4.3 动态增强

```js
comp = ctx.createDynamicsCompressor();
comp.threshold.value = -24;  comp.knee.value  = 6;
comp.ratio.value     = 3;    comp.attack.value = 0.003;  comp.release.value = 0.25;
```

只用**一个**压缩器。想做「多段压缩」得上 `ChannelSplitter` + 3 条独立压缩器再合并，
CPU 和三倍参数维护成本，对 44.1k 单曲试听不划算。

### 4.4 响度平衡

慢速 AGC，不用压缩器：

```
每 1.0s：读 analyser 的 RMS → dBFS
       target = clamp(-18 - dBFS, -6, +6)      // 目标 -18dBFS
       outGain.gain.setTargetAtTime(target, now, 1.5)   // 时间常数 1.5s，慢到听不出
```

时间常数是关键：小于 0.5s 会变成「抽吸感」，大于 3s 会跟不上段落变化。

### 4.5 空间音效

`ConvolverNode` + **程序生成 IR**（0 位图，符合仓库约束）：

```js
// 指数衰减噪声，2 声道，1.6s
const n = Math.floor(ctx.sampleRate * 1.6);
for (let ch = 0; ch < 2; ch++) {
  for (let i = 0; i < n; i++) {
    buf[ch][i] = (Math.random() * 2 - 1) * Math.pow(1 - i / n, 3.2);
  }
}
```

不用 `DelayNode` 反馈环，因为反馈环的音量用户没法预测，且容易自激。
卷积的 CPU 成本在 1.6s IR + 44.1k 下可接受（一次 FFT 分区卷积）。

### 4.6 母带（原「AI 母带」）

三段固定链，参数写死，理由是 §6：

```
EQ 微调（+1dB@120Hz 补偿，-0.5dB@3kHz 减刺）
→ 压缩（threshold -20, ratio 2, release 0.4）
→ WaveShaper 软拐点限幅（tanh 曲线，峰值 -1dBFS）
```

### 4.7 输出设备切换

**这是我在 `双风格-可行性分析.md` 里判断错的一条**，需要更正：不是「浏览器里拿不到」。

```js
if (ctx.setSinkId) await ctx.setSinkId(deviceId);   // Chrome/Edge 110+
```

但有三个真实限制，必须写进 UI，不能做假下拉框：

| 限制 | 后果 |
|---|---|
| 媒体元素被 `createMediaElementSource` 接管后，`audio.setSinkId()` **失效** | 必须调 `AudioContext.setSinkId()`，调错对象就是「切换了没反应」 |
| `enumerateDevices()` 的 `audiooutput` 项，**未获麦克风权限时 label 为空** | 只能显示「输出设备 1 / 2」，看不到「Realtek Speakers」 |
| 要拿到真实设备名，得申请 `getUserMedia({audio:true})` | 为一个下拉框弹麦克风授权，**不可接受** |

**建议**：只做「默认输出 / 输出设备 2 / 3…」的编号列表，并在旁边标一行小字
「设备名称需麦克风权限，此处按序号显示」。对方产品显示「未检测到输出设备」，
说明它可能也没走通这条路 —— 这反而是可以做得比它好的地方。

## 5. 六个必须处理的坑

这一节是本文档的核心价值。前两条会直接导致「功能看起来对，但用户听出错」。

### 5-1 `AudioContext.setSinkId` ≠ `HTMLMediaElement.setSinkId`
见 §4.7。图接管后元素级的 sink 不生效，**没有报错，只是没反应**。

### 5-2 音量双口径（最容易出事的一条）
引入 `outGain` 后，`audio.volume` 和 `outGain.gain` 都在衰减信号：

```
实际听感音量 = audio.volume × outGain.gain        ← 两个乘数
```

而 `viz.js` 的 VU/频谱读的是 `analyser`，位置在 `outGain` 之前，所以：

- 用户把音量拉到 10%，VU 表**纹丝不动** —— 这正确（录音室惯例）；
- 但如果 `audio.volume` 也参与，VU 读数就和它无关，用户会觉得「表在骗人」。

**做法**：`audio.volume = 1.0` 钉死，`app.js:927` 那行改为 `Core.setVolume(vol.value/100)` → `outGain.gain`。
`download.js:391` 那条关于音量口径的注释要同步更新，否则下一个人会按旧注释改回来。

### 5-3 改接线必须原子
开关「空间音效」时如果用 `disconnect()` 再 `connect()`，中间有 1 帧空隙 → **可听见的咔哒**，
严重时 Chrome 会把 chain 判为断链，直接静音。

**做法**：干湿双路常连，用两个 GainNode 交叉淡化：

```
input ─┬─► dry ──────────────┬─► sum
       └─► wet(卷积/压缩) ──► ┘
        dryGain.gain: 1 → 0     wetGain.gain: 0 → 1   （0.06s 线性）
```

整条链**从不断开**，只改两个增益。这条同时解决了 §5-3 和 §5-4。

> 与 `实现路径.md` §5 第 2 步「先用 `disconnect()` 拆旧的，再连新的」不矛盾，两者场景不同：
> **初始化**（`ensure()` 内，一次性）先断后连是对的，因为同一个同步块里改图，音频线程看不到中间态；
> **运行时**（用户切开关）绝不能断链，必须走上面的干湿交叉淡化。混淆这两个场景就会出现「切空间音效时咔一声」。

### 5-4 切预设爆音
所有参数变化禁止 `.value = x` 直接赋值，必须：

```js
p.setTargetAtTime(v, ctx.currentTime, 0.02);   // 20ms，够平滑且听不出延迟
```

`linearRampToValueAtTime` 也可以，但需要自己算 `cancelScheduledValues`，容易写出跳变。

### 5-5 bypass 必须是真 bypass
「直通」不是「把所有 gain 设 0」，而是干路 gain=1、湿路 gain=0。
截图那句「当前：直通，未做任何染色」给了 UI 一个明确口径：
**状态文案要反映真实链路**，接了什么就写什么，别写成营销文案。

### 5-6 44.1k 素材 vs ctx 实际采样率
`new AudioContext()` 默认跟设备走，大概率是 48000，素材是 44100 —— 浏览器会自动重采样。
两个后果：

- **不要**照抄截图写「48 kHz」，写素材真实值 44100（`OUT_RATE`）；
- EQ 的频率参数与采样率无关，不用做换算；但如果自己生成 IR / 波形，
  必须用 `ctx.sampleRate` 算长度，不能写死 44100。

## 6. 「AI 母带」这个词怎么办

对方敢写 AI，是因为它声称「分析你的曲库、生成母带基准」。本项目**没有推理后端**，
`build_web_pyi.py` 里也没有任何模型文件。三条路：

| 方案 | 做法 | 诚实性 | 建议 |
|---|---|---|---|
| A. 改名「自动母带」 | 固定启发式链 + 曲目自适应 | 完全诚实 | **推荐** |
| B. 保留 AI，UI 标「本地启发式」 | 同上，只是名字不变 | 勉强 | 不推荐，`README` 已强调离线可用，会被追问 |
| C. 后端接模型 | 需联网/打包模型，几十到几百 MB | 诚实 | **不做**，与单文件 exe 冲突 |

**方案 A 里有一件真事值得做**（这也是唯一能叫「自适应」的部分）：

```
分析当前曲目（约 200ms，离屏 OfflineAudioContext 或直接读 WAV 前 20s）
  → 频谱重心 centroid：< 800Hz 判定为「低频重」
  → 动态范围 crest factor：> 14dB 判定为「动态大、可压」
  → 据此自动选一条预设 + 决定母带压缩比
```

这是**真测量**，能被验收（给两首已知曲目，断言选出的预设不同），
比「点了按钮什么都没发生」强得多。命名建议：「自动母带（按曲目分析）」。

## 7. chiptune 素材的特殊性（本项目与对方最本质的差异）

对方是商业流行乐播放器，曲库是录音室作品；本项目产物是芯片音乐转换输出。三个差异：

| 差异 | 后果 | 调整 |
|---|---|---|
| 动态范围本来就小（方波 + 无混响尾巴） | 压缩器一压就「死」，听不出增强只听见变小 | 压缩比 ≤2，阈值 −20 起步 |
| 低音增强会糊方波边缘 | 「低音」预设 +8dB 后，bass 声部和旋律糊成一团 | 低频搁架上限 +4dB（对方 ±12） |
| 多数芯片高频截止 12–15kHz，无「空气感」 | 空气感 EQ 放大的是重采样噪声 | 12kHz 以上搁架 ≤ +2dB，且默认关 |

**预设建议重做，不照译**（对方 6 格是给流行乐分的）：

```
直通 / 芯片增强 / 低频暖化 / 空间感 / 轻柔母带 / 自定义
```

其中「芯片增强」= 中频微提 + 高频轻抬，让对方那种「人声/器乐」的语义换成对本项目有意义的语义。

## 8. 对双风格架构的修正

**音色引擎进内核，不进皮肤。** 原文档 §5 的 `Skin` 契约只覆盖「怎么画」，现在要加一层「能操作什么」：

```js
Core.tone = {
  preset: "bypass",
  bands:  [0,0,0,0,0,0,0,0,0],      // 9 段，两皮肤共用同一份数据
  flags:  { master:false, space:false, dyn:false, loud:false },
  volume: 0.72
};
Core.setPreset(id) / setBand(i,v) / setFlag(k,on) / setVolume(v)
Core.analyze()        // §6 的曲目分析，返回推荐预设，不改状态

Skin = {
  ...
  params: ["preset"],                       // deck：只暴露 2 个旋钮
  // 或
  params: ["preset","bands","flags","volume"]  // aurora：全暴露
}
```

**新增一条不变量**（补进原文档那三条之后）：

> 4. 皮肤**不得**自己创建 DSP 节点、不得直接改 `param.value` ——
>    只能调 `Core.setPreset/setBand/setFlag/setVolume`。
>    机械检查：`grep -n "createBiquadFilter\|createDynamicsCompressor\|createGain\|createConvolver" skin_*.js` 必须为空。

**好处**：Deck 只有 BASS/TREBLE 两颗旋钮，极光有 6 预设 + 9 段 + 4 开关 —— 但它们改的是
**同一份 `Core.tone.bands`**。切皮肤时音色不丢、不重算、不爆音。这正是「一个内核 + 两个渲染器」的定义。

## 9. 分期

| 期 | 内容 | 验收 |
|---|---|---|
| **T0** | 插链：`inGain → outGain → destination`，音量口径统一，无任何效果 | 出声正常；`audio.volume === 1`；VU 随信号动、不随音量动 |
| **T1** | 3 段 EQ + 6 预设 + 干湿双路骨架 | 切预设无爆音（录音自查）；「直通」时 `outGain` 前后采样一致 |
| **T2** | 压缩 + 软限幅 + 响度平衡 + 9 段 EQ | 各开关切换无咔哒；关闭全部开关后与 T0 输出波形一致 |
| **T3** | 空间音效（程序 IR）+ 设备切换 + 曲目自动分析 | IR 生成 <10ms；设备列表不空；两首已知曲目分析结果不同 |

T0 独立可提交，因为它已经把最危险的双口径问题解决了，后面的效果都是「往链里塞节点」。

## 10. 验收怎么做（不靠人耳的部分）

`test_web_ui.py`（3665 行起）已有 DOM 断言的习惯，本次加三类：

| 检查 | 方式 |
|---|---|
| 图结构 | 页面里执行 `Core.audioGraphNodes.length`，断言 ≥4（T0）→ ≥8（T2） |
| 契约 | `grep -c "createBiquadFilter\|createConvolver" skin_deck.js skin_aurora.js` = 0 |
| 直通等价 | 切「直通」后，用 `OfflineAudioContext` 跑 1s 素材，输出与原始信号 `max\|diff\| < 1e-4` |
| 音量口径 | 断言 `document.querySelector('audio').volume === 1` |
| 设备接口 | `typeof AudioContext.prototype.setSinkId === "function"` 存在时才渲染下拉框 |

最后一条尤其重要：**不支持就不渲染**，别给一个点了没反应的控件（对方那个「未检测到输出设备」就是这类）。
