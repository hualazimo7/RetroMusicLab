# 双播放风格（Deck / 极光）可行性分析

> 状态：可行性分析，未动产品代码
> 触发：在现有试听条基础上，再提供一套「AURORA 风格」播放界面，即**两种风格二选一**
> 前置：[`方案分析.md`](方案分析.md) · [`实现路径.md`](实现路径.md) · [`参考对象-REPLAY官网拆解.md`](参考对象-REPLAY官网拆解.md)

---

## 0. 结论

1. **可行**，但不是「再加一套皮肤」那么简单：两种风格的**几何方向相反**——Deck 是横向磁带机（≈2.4:1），
   极光是竖向大封面 + 右侧声音面板。硬塞进同一个 300px 高的展开条，两边都要将就。
2. 因此建议把承载方式从「dock 展开」升级为 **PlayerView 覆盖中间栏（stage）**：dock 仍是迷你条，
   点开后在中间栏铺开播放视图，两种风格是同一个 PlayerView 的**两个渲染器**。
   左栏音源列表、右栏转换设置始终可见 —— 试听不打断转换主流程。
3. 真正要设计的东西只有一个：**共用内核 + 皮肤契约**（§5）。三种东西必须共用（音频、分析器、传输状态），
   三种必须分叉（几何、材质、细节控件）。
4. **极光风格有三处在 RetroMusicLab 里没有数据源**（大封面、动态歌词、输出设备切换），
   必须先定替代方案，否则做出来是空壳（§2 表里列为「无」的三行）。

## 2. 极光风格拆成零件，逐条对表

从 README 的「正在播放」描述提炼（不是猜）：

| 元素 | 对方做法 | 本项目数据源 | 结论 |
|---|---|---|---|
| 黑金配色 | 黑底 + 金色描边/文字 | 有（主题变量体系现成） | **可做**，且可做成独立材质 |
| 大幅封面 | 专辑封面居中，占画面主体 | **无**：主界面 `app.js` 里没有任何 cover 概念（grep 无结果）；试听对象是转换产物 WAV | **必须替代**，见 §3 |
| 动态歌词 | 逐行高亮滚动 | **无**：chiptune 游戏音乐没有歌词数据 | **砍掉**，换「元数据跑马灯」 |
| 实时点阵频谱 | dot-matrix 点阵 | 有（`AnalyserNode`，`viz.js` 已在用） | **可做**，点阵比现有柱状更省 |
| 模拟 VU 表 | 双表指针 | 有（时域数据算 RMS） | **可做**，两风格共用同一套数学 |
| 玻璃 / 金属面板、透光 | 面板背面可调 | 纯视觉，无数据依赖 | **可做**，正好成为两风格的公共「材质参数」 |
| 氛围灯颜色与动态 | 可调 | 纯视觉 | **可做**，但要限性能（§8） |
| 九段 EQ | 9 段 −12…+12dB | 技术上能做，交互成本高 | **降级为 3 段**（低/中/高），别硬撑 9 段 |
| 音色预设（直通/低音/人声/器乐） | 5 档 | 可映射为 3 段 EQ 的预设 | 可做，成本低 |
| 输出设备切换 | 系统音频设备 | **无**：浏览器里拿不到 | **砍掉** |
| 音质信息条（格式/采样率/位深/码率/来源） | 底部一行 | **有**，而且本项目 `probe.py` 读得比它细 | 做成优势项 |

这张表的价值在于：极光风格**七成能落地，三成必须降级**。先认清这一点，才不会做到一半发现没数据。

## 3. 三处「没有数据」怎么补

**① 大幅封面。** 有两条现成来源，优先级从高到低：

1. **游戏封面**：下载页已经在抓图并落盘（`server.py:1551` `/api/dl/cover`、`web_ui/dl_api.py` 的 `cover_paths`），
   主界面复用同一份文件即可，只是要多一个 `/api/cover?id=` 之类的主界面接口；
2. **程序化封面**：没有封面时，用曲名哈希生成一组几何图形（圆环 / 波纹 / 渐层色块），**0 位图**，随主题变色。

两者都要有：前者让界面「像播放器」，后者让界面「永远不空」。对方是商业播放器，曲库都是带封面的音乐；
我们是游戏音乐转换工具，**空封面是常态**，程序化封面不是备胎而是主路径。

**② 动态歌词 → 元数据跑马灯。** 没有歌词，但有比歌词更硬的信息：机种、芯片、曲目号、时长、格式、采样率。
做成一行随播放缓慢滚动的「数据条」，视觉密度接近歌词，信息是真的。

**③ 输出设备 → 只读显示。** 显示「Web Audio / 浏览器输出」，不做切换。别做假下拉框。

## 4. 几何方向相反，这是本方案的核心矛盾

| | Deck（磁带机） | 极光（面板） |
|---|---|---|
| 骨架 | 横向，≈2.4:1；卡带窗 + 表盘 + 旋钮一排 | 竖向；封面（方）+ 信息条 + 频谱 + 右侧固定声音面板 |
| 需要的高度 | 200–300px 就够 | 竖屏布局，**低于 480px 会全挤在一起** |
| 需要的宽度 | 宽（横向排布） | 中等（封面是方的） |
| 主视觉 | 卷盘转动 | 封面 + 点阵频谱 |

**结论**：把两者都塞进 150–300px 的 dock 展开区，Deck 勉强够、极光必然残废。
所以承载方式要重新选。

### 三种承载方案

| | X 都在 dock 展开区（原方案） | **Y PlayerView 覆盖 stage（推荐）** | Z 分别承载 |
|---|---|---|---|
| Deck 效果 | 好 | 好（高度更宽裕） | 好（dock 展开） |
| 极光效果 | **残废**（高度不够） | 好 | 好（全屏） |
| 骨架数量 | 1 | **1** | 2（两套打开/关闭逻辑） |
| 对转换流程 | 不遮挡 | 只占中间栏，左右栏仍可操作 | 全屏时全遮挡 |
| 与已完成分析的关系 | 沿用 `实现路径.md` §1 | §1「改行高」被替换，其余全部保留 | 需要两套验收 |

**推荐 Y**，理由是「一块画布给两种比例让路」这件事本来就不成立；
而 `stage` 本来就是内容区，被播放视图占用语义正确，且不需要动 `.app` 的行高。

**对已写文档的影响**（诚实记账）：

| `实现路径.md` 小节 | 在 Y 下 |
|---|---|
| §1 展开改 `.app` 行高 | **作废**，改为 `stage` 内挂 `PlayerView` 层 |
| §2 包 `#deck` 一层、`deck-body` | 部分作废：改为 `PlayerView` 容器 |
| §3 频谱 canvas 搬家 | **保留**（仍从 inspector 搬进 PlayerView） |
| §4 viz 三接口 + rAF 保活 | **保留**，且现在更必要（两个皮肤都要读） |
| §5 音频图改造 | **保留** |
| §6 仪表数学 | **保留**（两皮肤共用） |
| §7 状态机 | **保留**，状态多一个「当前皮肤」 |
| §8 验收命令 | **保留**，`--deck` 改为 `--skin=deck\|aurora` |

## 5. 共用内核 + 皮肤契约（本次真正要设计的东西）

```js
/* player_core.js —— 只有一份，两种皮肤都只能通过它拿数据、发命令 */
Core.state = {
  skin: "deck",                  // 当前皮肤
  playing, id, name, fmt, sr, bits, br,
  dur, pos, volume, eq: { low, mid, high },
  live: false                    // 分析器是否有有效数据
};
Core.audio   // 单例 <audio>，只读引用
Core.viz     // VizKit 实例，只读引用
Core.on("state" | "frame" | "track", cb)
Core.play() / pause() / toggle() / seek(pos) / prev() / next()
Core.setVolume(v) / setEq({low,mid,high}) / setSkin(id)

/* 皮肤契约 */
Skin = {
  id: "deck" | "aurora",
  label: "磁带机" | "极光",
  mount(host, core),   // 建 DOM，可返回 Promise
  unmount(),           // 解绑事件、停自己的 rAF
  resize(),            // 容器尺寸变了
  onState(s)           // 只读状态推送
}
```

**三条不变量，写进注释也写进测试**：

1. 皮肤**不得**碰 `core.audio` / `core.viz` 的节点图（不 `connect`、不 `createMediaElementSource`）——
   否则会重演 `viz.js:11-21` 那三条坑，症状是「频谱漂亮但没声音」；
2. 皮肤**不得**写 `localStorage`，皮肤选择由 core 统一存 `rml-player-skin`；
3. 皮肤**不得**发网络请求 —— 数据都从 `Core.state` 来。

> 为什么必须这么定：第二个皮肤是「同一个坑再踩一次」的最大诱因。
> 有了契约，验收可以机械检查：`grep -n "\.connect(\|createMediaElementSource\|localStorage" skin_*.js` 必须为空。

## 6. 状态与持久化

| 项 | 值 |
|---|---|
| 存储键 | `rml-player-skin`（跟主题的 `rml-theme` 同前缀；`msu1.viz` 是 viz 的历史遗留键，不再新增同类） |
| 默认值 | `deck`（更贴本项目的复古硬件调性；首次升级不打扰用户） |
| 与 6 套主题的关系 | 材质不跟主题（沿用上轮结论）。极光的「黑金」是**固定材质**，正好对上 |
| 切换时机 | 播放中可切，不中断音频（只是换渲染器）；切换时保持 `pos` 与音量 |

## 8. 风险

| 风险 | 触发 | 影响 | 对策 |
|---|---|---|---|
| 两个皮肤代码分叉 | 后加的功能只改了一边 | 两套行为不一致，最难查 | 逻辑全在 core；皮肤只做「读状态 → 画」 |
| 有人绕过契约接线 | 图省事直接 `viz.an.connect()` | 静音，且只在特定皮肤下复现 | 机械检查（§5 的 grep）+ code review |
| 极光做出来是空壳 | 封面/歌词没替代方案 | 视觉塌，用户觉得「假」 | 程序化封面当主路径，不是备胎 |
| 性能三重叠加 | 点阵频谱 + 氛围灯 + 毛玻璃同屏 | 集显掉帧 | 一屏只允许**一个**全屏 blur，其余用渐变；低端减半刷新 |
| 名称与素材侵权 | 直接叫 AURORA、用对方截图 | 商标/版权风险 | 对外叫「极光」，素材全部自绘 |
| 打包漏文件 | 新增 `player_core.js` / `skin_*.js` / css | PyInstaller 版 404 | `build_web_pyi.py:49` 与 `build_web.py` 两处同步 |
| 与 0 位图约束冲突的误解 | 有人以为封面图违反约束 | 争论成本 | 写清楚：封面是**运行时数据**，不是仓库素材，不违反 0 位图 |

## 9. 待决策（进 P0′ 前必须定）

1. **承载**：X 都在 dock 展开 / **Y PlayerView 覆盖 stage（推荐）** / Z 分别承载。
2. **极光的三处降级**是否接受：无歌词 → 元数据跑马灯；无专辑封面 → 游戏封面 + 程序化封面；无输出设备切换。
3. **默认皮肤**：`deck`（推荐）还是 `aurora`。
4. **EQ 段数**：3 段（推荐）还是 9 段。
