## 二、这个工程到底是什么

Windows 桌面工具（Python 3.14 + PyInstaller onefile，63.4 MB 单文件），
把复古主机音源转成 **WAV** 或 **MSU-1 CD 音轨（BIN+CUE）**，并带一条完整的
「找资源 → 下载 → 解压 → 转换 → 上传云盘」流水线。

三个界面并存，**v5.5 只发 Web 版**：

| 界面 | 状态 | 说明 |
|---|---|---|
| Web 版（`msu1_web.py`） | **正式线** | 本地 HTTP 后端 + Chromium `--app` 窗口，HTML/CSS 可继续改 |
| tkinter 版（`msu1_gui.py`，v4.44） | 留档 | 8,744 行，旧界面最后一版，仍可跑 |
| Qt 版（`msu1_qt.py`，v5.0-qt） | 停更 | PySide6，99 MB / 冷启动 9 s，被 Web 版取代 |

代码规模（今日实测）：

## 四、已经做完的（按能力域）

### 4.1 转换核心

- 三条输出路径：**WAV 分轨** / **MSU-1 BIN+CUE**（含 PCM 打包）/ **单文件合并**
- 光盘镜像：`.cue` `.bin` `.iso` `.img` `.raw`，CD-DA 走 PyAV，静音盘自动改抽 XA-ADPCM，按静音间隔切曲
- PS1 的 `.txtp` / 0 字节子流式 txtp / 平铺 `.XA` 全支持（纯 Python，不要 BIOS、不要 foobar2000）
- 输出按游戏名分文件夹，每个游戏各自从 `01_` 编号，manifest 断点续转
- 长任务可取消、进度单调不倒退

## 十二、执行记录（2026-10-25 21:3x~22:2x）：v5.8 KSS 换解码器

### 触发

用户从 v5.7 新接的 Zophar 下载页下了 `Game Gear/Puyo Puyo`，转换报
`❌ G-3324.kss 转换失败：未产出任何 WAV（解码零产出，文件可能损坏或格式不受支持）`。

### 根因

**不是素材坏，是 libgme 的 KSS 实现残缺。** `Kss_Emu` 只映射
`0x0000-0x3FFF` 与 `0x8000-0xBFFF`，**不映射 `0x4000-0x7FFF`**。
32 KB 的 Game Gear rip 跨过中间 16 KB → 丢一半代码 → Z80 跑飞，
而 libgme **不报任何错**，`gme_play` 正常返回、每轨精确静音（peak == 0）。
上层 B18 的零产出判据命中，于是把解码器缺陷报成「文件可能损坏」。

决定性证据：**同一个 32,768 B 的 `G-3324.kss` 在 joshw 的
`kss.joshw.info/Game Gear/p/` 里一模一样**，libgme 同样解不了 —— 与 Zophar 无关。

试过但无效（都已实测，别重走）：

* 把 `load_len` 补到 `load+len == 0xC000` → 仍静音（不是 ROM 大小问题）
* 改 `bank_mode`（0x00/0x01/0x02/0x03/0x17/0x7A/0x80/0x81/0x90/0x91/0x97）→ 全静音
* vgmstream → 这版不带 KSS 支持，`failed opening`

### 修法

接 [libkss](https://github.com/digital-sound-antiques/libkss)（`kssplay` 核心库），
编成 `kss2wav.exe`，`.kss` 走外挂解码器（同 v5.5 的 WSR 路子）。

| 文件 | 作用 |
|---|---|
| `tools/kss2wav/kss2wav.c` | 基于上游 example，去掉 fade（流水线统一由 Python 侧做）与 loop 检测（时长由 m3u 给定） |
| `tools/kss2wav/build.py` | `zig cc -O2 -mcpu=baseline -DEXCLUDE_DRIVER_ALL`，29 个源文件 → 298,496 B |
| `tools/kss2wav/src/libkss/` | 整棵源码 2.5 MB，6 个 submodule 已展开（换机不用再 clone） |
| `kss_native.py` | 曲目表（复用 `_parse_sidecar_m3u`）/ `GAIN=4.0` / `decode_track` / `load_tracks` |
| `chip_decode.py` | WSR 与 KSS 合并成一个「外挂解码器」分支，`__import__(native)` |
| `chip_formats.py` | 新增 `KSS_EXTS`；修 `_m3u_text` 的 cp932 误判；顶部补 `import re` |

**音量**：libkss 混音比 libgme 低约 12 dB（实测比值 3.7~4.4），统一 `GAIN = 4.0` 再 clip。
**`.sgc` 不动**：独立容器，libgme 6/6 正常，没必要多起一个进程。

### 顺手修：m3u 编码误判

`_m3u_text` 原为「utf-8-sig → cp932 → latin-1，能解就用」。cp932 几乎不会失败

ASCII 字母/数字 → 改用 latin-1」（真日文是连续一段 `ｱﾙﾌｧ`）。修完 `©1993`。

## 十八、执行记录（2026-10-26 13:2x~14:3x）：v5.9.5 SPC 包转换「0% 卡住」

用户报：桌面的 `Chrono Trigger (EMU).zophar`（92 首 SPC）点「开始转换」，
界面一直 `转换中… 0%`，日志停在 `▶ [1/1]`，第 01 首「转换中」其余「等待」，
输出目录空的。附了截图。

**第一件事是判断「真死锁」还是「假死」**：查进程，`MSU1Converter-web` 在跑，
CPU 53 秒还在涨 —— 不是死锁，是在干活但不报告。

### 根因（两个，叠在一起才这么像死机）

1. **进度没接下去**
   `load_source()` 的 `.spc` 目录分支是裸调 `load_spc_dir(path)`，
   `on_progress` 没传。而 `load_spc_paths` **本身支持**（`_flush_spc_batch`
   每批结束 `prog(len(tracks), total, secs)`）。于是解码阶段零上报。
2. **白解 4 倍时长**
   `natural` 策略 = 解到「连续 2 秒静音」；循环曲永远等不到 → 撞
   `_SPC_MAX_SECS = 600`；`write_tracks()` 只留前 150 秒 → 450 秒白解。
   92 × 600 秒 = 15.3 小时音频 ÷ 约 50 倍速 ≈ 17 分钟。

**量化过程**（没有这一步就只会去「调大超时」）：

| 测什么 | 结果 |
|---|---|
| 8 首样本解码 | 4206.7 秒音频 / 84.8 秒 → **每首 600.0 秒**（全是循环曲） |
| 峰值扫描 `max(map(abs, …))` | 5056 块/秒 ≈ 470 倍速 → **不是瓶颈**（只占 10%） |
| 瓶颈 | libgme 的 `gme_play`，49.6 倍速，改不动 |
| 结论 | 唯一杠杆是**别解 600 秒** |

### 改法

`decode_cap` 一路透传：`load_source` → `load_spc_dir` → `load_spc_paths`
→ `_flush_spc_batch` → `_spc_decode_batch` → `--spc-cap` → `_spc_decode_file`。

`_spc_decode_file` 里关键是**分清「已知时长」和「解到静音」**：

```python
known_len = play_secs is not None
if not known_len and decode_cap:
    play_secs = float(decode_cap)
pcm = _spc_decode_track(gme, emu, SR, max_secs=play_secs,
                        stop_on_silence=not known_len)
```

`stop_on_silence` 仍是 `not known_len` —— 短曲照样按静音提前收尾，
只有永远等不到静音的循环曲才被上限截住。**不能**把 `decode_cap` 当成

## 二十、执行记录（2026-10-26 19:0x~19:3x）：v5.9.7 FLAC 输出

用户原话：「给主界面和下载音源界面都加一个转 flac 格式功能」。

### 设计：只换容器，不换音频

输出规格仍是设备固定的 16bit / 44100Hz / 立体声。FLAC 是逐样本无损，
解回来与原始 PCM **逐字节相同**，体积约 35%。所以整条解码链路一行没改，
只在最后「写盘」那一步换编码器。

**两页本来就共用同一个写盘函数** `spc_wav.write_tracks`（主界面
`convert_job` 和下载页 `dl_convert.ConvertWorker` 都收口在这里），
所以只加了一个 `fmt="wav"` 参数就同时覆盖两边。

### 新建 `flac_out.py`

不复用 `netease_cloud.wav_to_flac`：那个模块顶部把 pycryptodome / segno
这些可选依赖全拖进来，主转换流程只是「写个 FLAC」，不该为此把整条云盘
链路拉进内存（换台机器少装一个 pycryptodome，转换本身就会跟着起不来）。

`flac_out` 只依赖 numpy + soundfile。三个硬要求：

1. **int16 直通**（`dtype="int16"` / `dtype="<i2"`），绝不过 float32
2. **原子写**（`.part` → `os.replace`），失败不留半个 FLAC
3. **0 字节输出当失败**，不伪造成功

**从内存 PCM 直写**，不先落 WAV 再读回 —— 实测两条路径产物 md5 完全相同，
所以没有理由绕。33 首 150 秒立体声就是省掉 860MB 的写入 + 读回。

### 界面：1 + 2 布局 + 互斥

主界面右栏三张卡片：BIN+CUE 独占一行（另一种产物），WAV / FLAC 并排。
**三列不行** —— 340px 减 padding 只剩 ~316px，每格 ~100px，「BIN + CUE」
会被 `text-overflow: ellipsis` 截断。

WAV / FLAC **互斥**：同一段音频的两种容器，同时勾只会写两份。勾一个自动
取消另一个。`do_wav` 仍是「要不要出分轨音频」的总开关，`fmt` 只决定容器
—— 这样后端 `merged.get("do_cd") or merged.get("do_wav")` 的校验一行不用改。

下载页同理，两个复选框互斥，`dlMerge` 跟着 `auto_wav` 走。
⚠ 互斥逻辑用 `onchange` 而**不是** `onclick`：checkbox 的 `checked` 在
`change` 触发时已翻转完毕，`onclick` 里读到的可能是旧值。

### 五个只在真实转换时才炸的坑

1. `sf.read(dtype="int16")` 不能省 —— 过 float32 会被加 dither，
   文件能播、时长也对，**只是不等于原文件了**
2. `wav_scan_numbering` 只扫 `.wav` → FLAC 模式返回 `(0, set())` →
   第二轮编号从 1 重来、**覆盖上一轮**（R7 老 bug 换个扩展名复发）
3. `merge_wav` 用标准库 `wave` 读盘，读不了 FLAC → 每首失败刷屏
4. `_estimate_bytes` 按 WAV 估 FLAC 高估 3 倍 → 盘够却判空间不足 →
   连续 3 轮后 `cv_abandoned` **放弃剩余曲目**
5. 下载页「已转」状态只认 `.wav` → 选了 FLAC 每行都显示「未转」

还有一个「位置」坑：`fmt` 必须是 `write_tracks` 的**最后一个参数**。
`convert()` 内部是位置传参（`write_tracks(t, out, secs, log, prog, cancel,
used, idx, total)`），插中间会把 `log` 当 `cancel` 传进去 —— 不报错，
只是没日志、取消失灵。门禁里有一条专门盯这个。

> ① 路径：`D:/MSU1Downloads/joshw/QSound 街机（Hoot）\Mega Man 2 - The Power

> 文件格式为 qsflib+miniqsf，研究这种文件格式的转换
>

两句话拆成三件事：**(a) 把格式彻底逆向清楚**；**(b) 采样率统一到 44100**；
**(c) 接进主程序**。用户明确说 (b) 是 (c) 的前置条件。

### 关键判断

**① 这不是「一种音频编码」，是「一块街机基板的快照」。**
QSF 是 PSF 家族的一员（版本字节 `0x41`），里面没有波形。要出声必须跑 Z80 程序、
由它驱动 QSound DSP 的 16 个声道。和 PSF/USF/2SF/SSF/GSF 同一套思路，
所以施工路线可以直接照抄 `psf_native` / `gsf_native`。

**② 「重采样与其他机种一致」这句话的落点很具体。**
不是「加个重采样函数」，而是「**在解码器里出 44100**」。证据：

- `spc_wav.py` 的 `SR = 44100`，`write_tracks()` **恒定**写 16bit/44100/立体声；
- GSF 的原生率是 32768，也是靠 blip_buf **在解码器里直接出 44100**；
- `convert_job.py` **没有**重采样层 —— 各 `*_native.decode_pcm()` 的 PCM
  直接进 `write_tracks`。

所以放在 `qsf2wav.exe` 内部，`decode_pcm` 不传任何采样率参数。
这样 `spc_wav` / `convert_job` / `dl_convert` 三处**一行都不用改**。

**③ 24038 这个数字不能改。** `qsound_set_rates(state, 8000000, 250, 24038)`
里它是 QSound DAC 的硬件节拍（`60000000/2/1248 = 24038.46`）——
混音器每输出一个样本就按它推进一次 DSP。改大只会让整首变调（快 1.834 倍）。

### 四个坑

**① 非 ASCII 路径：`fopen` 打不开，报错却像「格式不对」。**
`QSound 街机（Hoot）` 走 ANSI 码页直接失败，解码器报
`ERR 不是合法的 QSF` —— 看起来像格式判断错了，其实是文件根本没打开。
修法照 `check_nonascii_path.py` 的老套路：`xfopen()` 先试原样 → 失败转宽字符
→ **先 `CP_UTF8` 再 `CP_ACP`** 各试一次。附带发现 Git Bash 的 `/d/...` 传进来是

**② CRC 算在 zlib 压缩体上，不是解压后。**

它**有**。按解压后校验会一直不匹配、误判文件损坏。

**③ `--rate 24038` 把 45 秒标成 82.6 秒。**

不是运行时变量 `out_rate`。于是 24038 分支按 44100 算帧数、再按 24038 除回来。
改成 `out_rate` 后帧数 1,081,710 = `45 × 24038`，严丝合缝。
（peak 值 5561 一直是对的，说明直通分支的采样逻辑本身没问题 —— 只有帧数算错。）

**④ `t_qsf` 里 `length_tag` 的合成样本写错了。**
第一版写 `b"[TAG]length=0:45\n"`，而正则用 `^length=`（`re.M`），
贴在 `[TAG]` 同一行匹配不上。真实标签区是 `[TAG]\ntitle=…\nlength=0:45`。
**门禁当场抓出来** —— 这就是不该手写合成样本糊弄过去的原因。

### 一条概念性守卫

QSound 是街机板上的**独立声音子系统**，**没有主机 BIOS**。所以：
`qsf_native` 里没有 `find_bios` / `set_bios` / `check_bios`；diag 的 `qsf` 段
没有 `bios` 字段；坏文件的报错文案**不许出现 BIOS**。三条都有门禁断言盯着。
照抄 `psf_native` 把 BIOS 检查带过来是概念性错误 —— 用户会去翻 BIOS 目录白忙。
