## 1. 核心事件一：MP3 持续杂音（v5.9.18 修复）

### 1.1 现象
用户报：转 MP3 一定有持续杂音，音质奇差，声音一大就「兹拉兹拉」。听的是 GBA 的
*Advance Wars*（注意：不是 NES，是 GBA），且确认**是新转的**，不是历史遗留。

### 1.2 根因（已定位，确定）
`libsndfile 1.2.x` 的 MP3 编码器**不认 int16 输入**。把 `-32768..32767` 的整数数组
直接交给它，它按 float 样本（本该是 `-1.0..1.0`）解释 → 每个采样点被放大约 32768 倍
→ 立即削顶成 ±1 的方波 → 写出来就是满耳噪声。

| 输入方式 | SNR | 相关系数 | 听感 |
|---|---|---|---|
| int16 直传（旧 bug） | **-21.6 dB** | ≈0.3 | 持续兹拉兹拉，越响越明显 |
| float32 归一化（修复后） | **+36.4 dB** | 0.9999 | 正常 MP3 |

归一化**必须除 32768**（不是 32767）：让 `-32768` 正好落到 `-1.0`，与 soundfile
自己的 int→float 口径一致，0 dBFS 不越界。

顺带修掉第二个坑：libsndfile 的 MP3 码率**只受 `compression_level` 控制**，且
**必须显式 `bitrate_mode="CONSTANT"`**，否则默认 VBR。修复前说明书写的「320 kbps CBR」
实际是 102 kbps VBR。

### 1.3 为什么一年多没人发现（重要教训）
坏文件的**所有结构指标都是对的**：能播、时长/帧数一致、采样率/声道一致、体积甚至更
「像」320k、帧结构自洽（手工按 ISO 11172-3 走帧）、三个独立解码器解出来一致。
唯一能分辨的是「**解回来跟源逐样本比 SNR**」—— 坏文件 -21.6 dB，好文件 +36 dB。

> **铁律：体积 / 时长 / 能解码，都不能推断内容对不对。唯一判据是解回来和源比。**

### 1.4 代码落点（`msu1-to-cd/flac_out.py`，`_write()` MP3 分支）
```python
kw["compression_level"] = 0.0
kw["bitrate_mode"] = "CONSTANT"
# 输入 arr 必须是 float32，且已 /32768.0 归一化（见 _write 上方归一化逻辑）
```
修复后实测码率 **321 kbps CBR**，SNR 36~43 dB。

## 2. 核心事件二：MP3 落盘自检（v5.9.19 做进产品）

把上面对付 bug 的「唯一有效检查」搬进产品代码，防止同类问题再无声无息地发出来。

### 2.1 实现（`flac_out.py`）
- 新增 `verify_lossy(path, arr, sr, ...)`：每写一首 MP3，落盘（`os.replace` 之前）
  立刻解回来，取中段最多 3 秒，跟源比三项指标。
- 判据常量（文件顶部）：
  - `VERIFY_MIN_SNR = 8.0`
  - `VERIFY_MIN_CORR = 0.80`
  - `VERIFY_MAX_PEAK_RATIO = 1.6`
  - `VERIFY_MAX_SEC = 3.0`
  - `VERIFY_SILENT_PEAK = 100`
- 任意一项不达标 → 抛 `OSError`、删掉半成品 `.part`，这首判失败。
- **特例跳过**（不误杀）：静音（峰值 < 100）/ 太短（< 2048 帧）/ 自检自身异常。
- FLAC 是无损，**不跑**这条自检（跑了只会白白慢一倍）。

### 2.2 阈值为什么是 8 dB 而不是 20 dB
满量程白噪（合法内容）的 SNR 只有 **15.3 dB**。阈值设 20 dB 会把这种合法内容误判失败。
实测余量：正常音乐 36~43 dB / 0.9999 / 1.02~1.12；满量程白噪 15.3 dB / 0.99 / 1.00；
老 bug -21.6 dB / 0.1 / 2.0。所以取 8 dB 主判（SNR+相关），峰值比 1.6 仅作补充。

### 2.3 版本门控（`dl_convert.py`）
```python
AUDIO_WRITER_VERSION = "6.0.0"   # v6.0.0 推进；v5.9.19 时为 "5.9.19"
BAD_BEFORE = {"mp3": "5.9.18"}   # v5.9.18 及之前的 MP3 视为坏，需要重转
```
`already_done()` 的第三道校验：源 MP3 的写入版本落在 `BAD_BEFORE["mp3"]` 之前 → 判「需重转」。
版本比较按**数字元组**（`(5,9,18)`），不是字符串，避免 `5.9.2` < `5.9.18` 这类误判。

### 2.4 验证结论
- 三解码器交叉验证（libsndfile / FFmpeg(PyAV) / dr_mp3(miniaudio)）解同一文件，
  互相 SNR 98~101 dB（最大差 1 LSB）→ 文件完全符合标准，换播放器不会变味。
- 误差在每个频段都稳定在 -72 dBFS 以下，无异常频段；预回声 -56.3 dBFS，无 MDCT 沙沙声。
- 「16k–20k 只有 17 dB SNR」是**误导性指标**：该频段源能量本身只有 -30.8 dB，除法
  得到难看数字但无听觉意义。不要单独用分频段 SNR 当判据。
- 编码器对比：lameenc（标准 LAME）全带 30.18 dB，反而比 libsndfile 的 37.38 dB 更差
  → **不换编码器**（libsndfile 内部就是 LAME 3.100，参数调得更合适）。

## 6. C 盘暴涨根因与处理（2026-10-27 追加）

### 6.1 现象
C 盘可用从 63 GB 掉到 31 GB。`C:\Users\xqh\.workbuddy-ai` 从 8.8 GB 涨到 35 GB。

### 6.2 真因
**AI 工具在删除文件前会先复制一份到会话目录**以支持撤销。清掉的 40 GB 里不在排除名单
的都被复制到了 `C:\Users\xqh\.workbuddy-ai\workspace\sessions\<会话id>\modify_backup\`。
其中 `D:\MSU1Temp` 等**不在排除名单**里（反例：`%LOCALAPPDATA%\Temp` 在名单里，没被备份）。

### 6.3 已处理
按用户确认清掉会话备份：`modify_backup/` 29 GB（31,781 文件）→ 15 MB；
`.workbuddy-ai` 35 GB → **6.4 GB**；`workspace/` 29 GB → 46 MB。

### 6.4 回收站
清理走回收站，回收站当时占约 33 GB（C 12 GB + D 21 GB），由**用户自行清空**
（最终 C 剩 8.5 MB、D 剩 15 MB）。清空后磁盘：C 可用 73 GB、D 可用 298 GB。

### 6.5 以后怎么避免
清大目录时预料到工具会复制一份到 C 盘（量级 ≈ 被删体积）。要么清完顺手清会话
`modify_backup/`，要么把常用临时目录加进会话的 `excluded_backup_roots.json`
（目前 `D:\MSU1Temp` 不在名单里，是这次暴涨的直接原因）。

### 11.2 档位为什么是 q10（`OGG_LEVEL = 0.0`）

`compression_level` 是 1.0−q/10，所以 q10 = 0.0。低档位不是「省体积」，是**自检过不去**：

| level | 体积占 WAV | 满量程白噪 SNR | 满量程方波 SNR |
|---|---|---|---|
| 0.0（现在） | 28% | 10.39 dB | **9.95 dB** |
| 0.1 | 20% | 9.00 dB | **3.21 dB** |
| 0.2 | 13% | 8.81 dB | **0.82 dB** |

方波是 **NES / GB 声道的真实音色**，不是刁难。OGG 的自检门槛因此单独定为
**6.0 dB**（MP3 是 8.0 dB）—— Vorbis 的误差结构不同，用 MP3 的门槛会误杀。

### 11.3 ⚠ 本轮最大的坑：libsndfile 写长 OGG 会**栈溢出杀进程**

**症状**：转一首 2 分半的曲子，进程直接消失 —— 没有异常、没有日志、
盘上留一个 `.part`。Windows 退出码 `0xC00000FD`（STACK_OVERFLOW）。

**边界（44.1k / 立体声 / float32，一次性 `sf.write`）**：

| 时长 | 结果 |
|---|---|
| 8 / 10 / 12 / 14 / 16 秒 | 正常 |
| 18 / 20 / 40 / 80 / 150 秒 | **崩溃** |

同一段音频 **FLAC / MP3 一次性写到 900 秒都没事** —— 只有 OGG 有这毛病。

**修法**：`flac_out._sf_write()` 分块喂，`OGG_BLOCK_FRAMES = 44100 * 5`（5 秒）。
5 秒离 17 秒边界有三倍余量；Vorbis 是流式编码，分块不影响码流。
实测分块写 20/60/150/300 秒全部正常。

**教训**：短样本（4 秒、5.76 秒）验不出这个问题 —— 之前的专项用例全用短音频，
一路绿灯。是拿真实曲库（150 秒）跑才炸出来的。**新格式必须用 ≥30 秒真素材验一次。**

门禁里加了一条**子进程**用例（40 秒），真回归了也是子进程崩、门禁照常报 `[FAIL]`，
不会让整个门禁静默死掉。

### 11.4 体积实测（真实曲库，9 首 / 7 个机种 / 32~159 秒）

| 格式 | 占 WAV |
|---|---|
| FLAC | **47.4%**（单首 24.8%~68.9%） |
| MP3 | **22.7%**（CBR，恒定） |
| OGG | **26.8%**（单首 21.1%~28.9%） |

> 旧说明书写的「FLAC 约 35%」是流行乐的典型值；**芯片音乐噪声多、熵高，压不到那么小**。

### 12.2 四条需求各自的实现要点

**需求 1：上传云盘可选 FLAC / MP3**

四层口径必须同时改对，漏一层就是「界面能选、实际还是 FLAC」：

1. 转码层 `wav_to_audio`：FLAC **必须 int16 直通**（float 中转会被加 dither）；

## 13. v6.0.2 追加：流式音频转 FLAC / MP3 出 WAV（2026-10-28 09:20）

### 13.1 用户报障与复现

> 「对于机种 Wii 我下载完后点击转换 FLAC 和转换 MP3，检查结果发现还 WAV
> 格式，`D:/MSU1Downloads/joshw/Wii` 目录下的 FLAC 和 MP3 文件夹中均为 WAV。」

实测：`FLAC/<游戏>/01_BGM_Adventure1.wav` 前 4 字节是 **`RIFF`**，
5,995,052 B；`MP3/<游戏>/` 里的同名文件**逐字节相同**（同一次解码的产物）。

### 13.2 根因：`fmt` 只在一个地方生效，注释却写着「只有一处」

`ConvertWorker.__init__` 的原注释：

```python
#: 全类只有一处真正用到它：传给 spc_wav.write_tracks —— 因为
#: 所有写盘路径（芯片音源 / PSF / 外挂解码器 / CD 音轨 / txtp）最后
#: 都收口在那个函数里。
```

**这句话是错的**（说的是主界面 `convert_job` 那条两段式链，不是下载页）。
实际有两条写盘路径：

| 路径 | 谁走 | fmt 是否生效 |
|---|---|---|
| 解码出 PCM → `spc_wav.write_tracks(fmt=…)` | `id666` / `chip` / `psf` / `usf` / `vio` / `ssf` / `gsf` / `qsf` | ✅ |
| 各模块自己的 `convert_one`（内部 `wave.open`） | `stream` / `cd` / `xa` / `txtp` / `pivotal` | ❌ 恒写 `.wav` |

所以 Wii（`.brstm`）、PS3（`.xvag`）、PSP（`.at3`/`.hca`）、3DS（`.laac`）、
Wii U（`.fsb`/`.btsnd`）、Xbox（`.xma`/`.bik`/`.araw`）、PS2（`.adx`），
以及 CD 音轨 / `.XA` / `.txtp` / GC 的 Pivotal `.psf` —— 选 FLAC/MP3/OGG
全部退化成 WAV。`WAV/` 目录本来就该出 WAV，所以「转 WAV」上看不出来。

### 13.3 改法（三处，缺一不可）

| 位置 | 改动 | 为什么缺了不行 |
|---|---|---|
| `dl_convert.ConvertWorker._reencode_to_fmt()` | 分派之后、⑤ 统计之前，把 `sub["files"]` 里的 `.wav` 编成目标格式、删中间 WAV、换路径 | 这是主修。一处收口 → 以后新增任何 WAV-only 解码器自动覆盖；幂等，芯片那条路径走到这里原样放过 |
| `ConvertManifest.already_done()` 第四道校验 | 记账名单里一个目标扩展名都没有、且含 `.wav` → 判「需重转」 | 没有它，升级后再点只会「已转过，跳过」，用户无法自救 |
| `ConvertWorker._drop_stale_products()` + `ConvertManifest.stale_records()/forget()` | 重转前把该目录里**所有**坏记录一次清掉（含文件与记账） | 编号是目录级的（`_scan_bucket` 接着最大号编）。只清当前源的话，目录里还剩 30 个旧 WAV，新文件从 `31` 起 —— 用户拿到「31 个旧 WAV + 31 个新 FLAC」，比不修还乱 |

为什么不给那五个 `convert_one` 各加 `fmt` 参数：它们各自还要处理重采样、
截断淡出、`used` 去重、`start_idx` 连续编号，塞进去等于在五个模块里各写
一遍编码分支；而且以后新增解码器还得再想一次。

### 13.4 顺带修的两条「静默跳过」（只补提示，不改行为）

## 14. v6.0.3 追加：试听条进度可拖 + 上一曲 / 下一曲（2026-10-28 09:50）

### 14.1 报障原文

> 「下载音源界面的播放器进度无法调节，也没有下一曲、上一曲按钮」（附截图）

### 14.2 根因

**进度条不是「拖起来卡」，是压根没绑事件。**

```html
<!-- 旧 -->
<div id="dlPlayBar" class="dl-play-bar"></div>
```

`style.width` 由 `audio.ontimeupdate` 每 250ms 写一次，除此之外没有任何指针
监听 —— 点上去等于点在背景上。

还有第二个坑，**只绑事件也修不好**：`ontimeupdate` 每 250ms 把宽度写回当前
播放位置。用户拖到 60%，下一帧被拽回 3%，表现就是「拖不动」。

第三个（布局）问题：进度条当时嵌在曲名那一行里，宽度只有约 150px，
就算绑了事件也很难点准。

### 14.3 改动

### 14.4 三条实现要点（以后改这里别再踩）

1. **Pointer Events + `setPointerCapture`** —— 鼠标 / 触控笔 / 手指一套代码。
   别写 `mousedown` + `touchstart` 两份。
2. **拖动期间必须让 `ontimeupdate` 让位**（`S.seeking`）。这是「拖不动」的

### 16.2 官方 API 断在哪（别再试了）

2026-10-28 本机实测：

| 端点 | 结果 |
|---|---|
| `images.igdb.com`（图 CDN） | **200，真 PNG** |
| `api.igdb.com/v4/*` | 401 —— 可达，只缺鉴权 |
| `id.twitch.tv/oauth2/token` | **不可达**：DNS 被污染到 `31.13.64.7` / `2a03:2880:…face:b00c:…`（Facebook 地址段）。走本机代理 `127.0.0.1:6686` 也是 `502 tunnel` |

### 16.3 为什么 `design.zaparoo.org` 是可行的替代

它是 **Zaparoo Designer**（NFC 卡片标签开源项目）的公开后端：

```
GET /api/search?searchTerm=<名字>&page=<页>&platformId=<IGDB 平台 id>
```

- **零鉴权**（无 API key、无 token、无 Referer 校验）；
- 返回**IGDB 原始 game 对象**（`name` / `cover.image_id` / `platforms[]`）；
- `cover.url` 指向 `images.igdb.com` —— 那个域名本机可达。

所以「曲线救国」= 用它替我们换 token + 转发查询，用 IGDB 自己的 CDN 下图。

⚠ **它是别人的公益服务，不是官方 API。** 这几条写死在 `cover_igdb.py` 里：

| 约束 | 常量 | 理由 |
|---|---|---|
| 请求间隔 ≥0.35s | `MIN_GAP` + 模块级锁 | 别当 CDN 刷 |
| 最多翻 2 页 | `MAX_PAGES` | 再多就是搜到一堆不相干的 |
| 只认 PNG | 校验 `\x89PNG\r\n\x1a\n` | IGDB 对不存在的尺寸会**自动降级成 JPEG**；光看状态码会把 JPEG 存成 `.png`，嵌 FLAC 那一步才炸 |
| 失败不影响下载/转码 | 每条目单独 `try` + 外层兜底 | 封面是锦上添花 |
| 它是**兜底**不是替代 | `_cover_one` 里 libretro 先试 | libretro 强的机种根本走不到它 |

### 16.4 踩过的坑：搜索词（这段最重要，别再踩）

第一版写完后 `vendor/_probe_igdb.py` 跑出 **56 条全部 0 命中**，而手工单条
调用明明是通的。

**原因**：把 joshw 的条目名**原样**当 `searchTerm` 发出去。joshw 名字长这样：

```

```

圆括号是日期/发行商，方括号是机种 —— 全是本地元数据。而 `/api/search` 对
`searchTerm` 是**近乎全等**的匹配：

| searchTerm | 结果 |
|---|---|
| `Chrono Trigger (1995-03-11)(Square)[SNES]` | **0 条** |
| `Chrono Trigger` | 1 条 |
| `chrono trigger` | 1 条 |

**修法**：`_terms(title)` 拆成候选词，按顺序试，首个命中即停：

1. `_strip_blocks()` —— 去 `(...)` / `[...]`，**保留原始大小写**

2. `cover_art.norm_title()` —— 归一化 → `chrono trigger`

3. **副标题前缀** —— `Final Fantasy VII - Something` → `Final Fantasy VII`
   （和 `cover_art.pick` 那条 ` - ` 规则同源，最后一档兜底）。

修完同一批 56 条 **0% → 68%**。

⚠ 这个坑难发现是因为**它失败的样子是「静默返回空表」**：界面只显示
「没找到」，和「这个游戏 IGDB 真没有」完全分不清。所以 `t_v605` 里有一组
断言专门守这个 —— 拦住**发出去的 URL**，不只看最后有没有图：

```python

_mark(all("(" not in t and "[" not in t for t in sent), ...)
```

## 17. v6.0.6 追加：「衍生 WAV」去重 —— FLAC 20 个 / MP3 10 个（2026-10-28 13:40）

### 17.1 用户要什么

> 「同一个游戏转出的 flac 数量和 MP3 数量不同，以 PS4 为例
> `D:/MSU1Downloads/joshw/PlayStation 4\FLAC\Assetto Corsa (2016-08-25)(Kunos Simulazioni)(505 Games)[PS4]`；
> `D:/MSU1Downloads/joshw/PlayStation 4\MP3\Assetto Corsa (2016-08-25)(Kunos Simulazioni)(505 Games)[PS4]`」

实测 FLAC 20 个、MP3 10 个，而且**成对**、字节数完全相同：

```
01_full_a-proud-moment_0117 {6db25559…}.flac        9,971,553 B
02_full_a-proud-moment_0117 {6db25559…}.fsb.flac    9,971,553 B   ← 同一段音频
```

### 17.2 根因

源目录里同时有：

```
…\Assetto Corsa (…)[PS4]\
    116_full_a-proud-moment_0117 {uuid}.fsb       2018-02-10   joshw 原始音源
    116_full_a-proud-moment_0117 {uuid}.fsb.wav   2026-10-28 13:14   我们自己转的
```

`.fsb` 是 Wwise 音库（真音源）；`.fsb.wav` 是「转 WAV」那一步的**产物**，
但它被写在**源文件旁边**（不是写进 `WAV/` 输出目录）。而
`is_convertible()` 只看扩展名，对两者**都返回真** —— 于是「转 FLAC」
把它们当成两首不同的曲子，各转一遍。

`.txtp` 完全同理：`xxx.txtp` + `xxx.txtp.wav`（AC4 源目录里 186 对）。

### 17.3 为什么 MP3 是 10、FLAC 是 20

记账（`.msu1-convert.json`）里的时间戳还原了时间线：

| 时间 | 动作 | 当时源目录里有什么 | 产出 |
|---|---|---|---|
| 13:13 | 转 MP3 | 只有 `.fsb` | 10 个 ✅ |
| 13:14 | 转 WAV | — | 10 个 `.fsb.wav` |
| 13:14 | 转 FLAC | `.fsb` **和** `.fsb.wav` | **20 个** ❌ |

**不是「MP3 少转了」，是「FLAC 多转了一倍」。**

### 17.4 修法：两半，缺一不可

#### 第一半 · 止血 —— 枚举阶段就滤掉衍生 WAV

`dl_convert.py` 新增：

```python
def is_derived_wav(path) -> bool:
    """xxx.fsb.wav，且同目录下 xxx.fsb 真的存在 → True"""
    s = str(path or "")
    if not s.lower().endswith(".wav"):
        return False
    base = s[:-4]
    if not base:
        return False
    try:
        return is_convertible(base) and os.path.isfile(base)
    except OSError:
        return False

def drop_derived_wavs(paths) -> list:
    """批量过滤，保序、同批内 A / A.wav 也丢 A.wav、不抛"""
```

判据的关键是「**base 必须真的存在**」：

| 输入 | 结果 | 为什么 |
|---|---|---|

### 18.4 ⚠ 端到端抓到的真 bug（单测全绿时漏掉的）

**现象**（起真 exe 走 HTTP）：

```
/api/dl/covers → n = 7
  i=0  200  247077 B
  i=1  200  247077 B     ← 和 i=0 一模一样
```

**根因**：去重只发生在**内存**里。`_cover_many` 拿到 7 张、md5 去掉重复的
一张、返回 6 张 —— 但 `_lookup.json` 里那 7 条**一条没动**。
`/api/dl/covers` 读的是表，于是又读回 7 张。

**修法两处**：

1. **写入侧**：`cover_art.set_covers()` 把去重结果回写查找表
   （`_cover_many` 里把 `raw` 从二元组改成 `(path, 来源, kind)` 三元组，
   去重后取前三元组拼相对路径写回）。
2. **读侧**：`cover_art._dedup_by_size()` —— `covers_for_title()` 返回前
   再按内容去重一次。**先比大小（`os.stat`，本来就为判存在做过），
   只有大小相同的才读文件算 md5**。实测 6 张里通常只有 1 组同大小，
   多读约 200 KB。

> **第 2 条是我额外加的，不在用户需求里**，交付时在
> `更新说明-v6.0.7.md` §8 里单独标出来了。理由：写回只能保证「从这次之后
> 表是干净的」，挡不住老版本写脏的表、或表被手工改过。读侧兜一层，
> 「轮播 N 张一定互不相同」才是接口的硬保证。用户若不想要，删掉
> `_dedup_by_size()` 的调用即可，写回那处仍然有效。

**修完再跑**：`n = 6`，6 张字节互不相同，`i=99` 夹住回 200，
不存在的游戏回 404 —— **全部通过**。

### 19.3 最要紧的一条：不许搞乱用户正在看的东西

批量更新跑在后台，`self.key` / `self.entries` / `self.sel` 一概不碰。

### 19.4 两个容易踩的坑

## 20. v6.0.9 追加：游戏列表每一列都能拖宽窄（2026-10-28 16:35）

### 20.1 用户原话

> 「@image#1 音源下载的游戏列表只有英文名称列可以调整大小，其他几列无法调整。」

### 20.2 根因：不是把手没挂上，是默认列宽装不下

先把「把手在不在」这件事排除掉：`initCols()` 从 v6.0.1 起就给每一列挂了
`.c-grip`。真正的问题在**默认值溢出**。

用 CDP 探针量用户截图那个窗口：

```
wrap.clientWidth = 648
可用宽度 = 648 − COL_PAD(24) − COL_GAP(8) × 7 = 568
```

而当时 `COL_DEF` 里六个非名称列合计 **478**，名称列本该吃 `568 − 478 = 90`，
但 `COL_MIN.name = 120` —— 于是被撑到 120，**总宽 598，溢出 30px**。

连锁反应解释了用户看到的全部现象：

| 现象 | 算式 |
|---|---|
| 拖别的列没反应 | 变宽要从名称列借，而 `slack = max(0, 568 − 598) = 0` |
| 名称列也拖不动 | 同上，它能借的余量也是 0 |
| 更早一层 | `initCols()` 在 `boot()` 里跑，那一刻 `clientWidth` 还是 **0**，`colAvail()` 算出来的「可用宽度」是假的 |

**关键认知**：`--dl-cols` 的最后一列是 `1fr` **空轨道**（行里只有 7 个格子）。
它只吃「剩余」空间，**不会**替溢出的部分买单 —— 所以总宽超过可用宽度时，
横向溢出是实打实的，不会被子轨道吸收。

### 20.3 四处改动

**① `colLaidOut()` + 两帧 `refit()`**（`web_ui/download.js`）

```js
}
```

**为什么是两帧**：实测第一帧 `clientWidth` 仍然是 0，第二帧才是真值。
一帧不够。

名称列吃剩余空间后如果低于下限，就把溢出量从**最宽的非名称列**里扣，

## 21. v6.0.10 追加：列宽改成「每列独立」+ 横向滚动（2026-10-28 18:10）

### 21.1 用户原话

> 「英文名称列向右拉，日期、大小、状态列不动，中文名列被压缩；
> 中文名列向右拉，结果日期、大小、状态列还是不动，英文名称列被压缩。」

### 21.2 这是模型问题，不是 bug

v6.0.9 修的是「**根本拖不动**」（默认值溢出 30px，名称列贴死下限）。
那个确实修好了。但**分配规则**还沿用了 v6.0.1 的思路：

> 表格总宽锁死正好填满窗口 → 某一列变宽必须有人让位 →
> 让位顺序「名称列优先，然后中文名」。

名称列和中文名各有 60px 余量，**永远是这两列在互相抢**；日期/大小/状态
没有余量，就永远不动。用户看到的现象是这套规则的必然结果。

### 21.3 用户选的新模型

两个方案里用户明确选了「**谁都不让，出滚动条**」：

> 拖谁只改谁，其它列宽度和位置都不变，合计超了就出横向滚动条。

### 21.4 实现

**`web_ui/download.js`**

- 删掉 `colRoom` / `colGive` / `colFit` 三个函数 —— 它们就是「互相借宽度」
  的实现，留着迟早被误用。门禁里有一条专门断言它们**不在**源码里。
- `colDrag` 的 `move` 只剩一行：

  ```js
  cols[key] = Math.max(COL_MIN[key], Math.round(start + ev.clientX - startX));
  colApply();
  ```

  不再备份 `startCols`、不再向任何人借。
- `colApply()` 除了写 `--dl-cols`，还写 `--dl-w`：

  ```js
  w.style.setProperty("--dl-w",
    Math.round(colTotal(cols) + COL_GAP * 7 + COL_PAD) + "px");
  ```

  `--dl-w` = 列宽合计 + 7 个间隙 + 左右内边距，给 CSS 的 `min-width` 用。
- 新增 `colSyncHead()`：表头**不在**滚动容器里（`.dl-rows` 只装行），
  横向滚动时靠 `transform: translateX(-scrollLeft)` 跟着走。挂在
  `#dlRows` 的 `scroll` 上，`colApply()` 里也顺手调一次（列宽一改，
  可滚动余量跟着变，`scrollLeft` 可能被浏览器夹回 0）。
- `colLoad()` 不再 `colFit`。存档 key 从 `msu1.dl.cols` 升到
  `msu1.dl.cols2` —— 旧的「总宽锁死」分布套到新模型上会一打开就溢出，

### 23.1 用户原话与选择

> 「没动，阈值比例现在应该调高还是调低」

我给了两个方案：

> **A（推荐）**：加「数字序列必须一致」判据，阈值不动
> **B**：只把阈值调到 0.92

### 23.2 阈值为什么救不了（这一版的核心论证）

`pick()` 原来三层判据：① 归一化全等 ② 副标题前缀 ③ 相似度 ≥ `MIN_RATIO`。
问题出在第三层：**续作只多一两个字符，名字越长这点差异占比越小**。

反推公式：名字长 `L`，续作多 2 个字符，相似度 ≈ `2L / (2L + 2)`。
临界点 `L ≈ 6` —— 也就是说只要名字超过 6 个字符，续作基本都能过 0.86。

拿用户机器上真实的 nsf 封面库（13835 条 / 3185 个不同名）算了一遍：
库里同时存在「正传 + 续作」的名字对 **136 对，其中 115 对（85%）
相似度 ≥ 0.86**，最长的到 0.98。**这条阈值对最常见的那类错配基本无效。**

更要命的是**错的和对的混在同一区间**：

```
0.930  caltron 6 in 1   → caltron 9 in 1              错（6合1 vs 9合1）
0.947  castle quest     → castlequest                 对（就少个空格）
0.957  ultraman club kaijuu daikessen → …dai kessen   对（断词不同）
0.958  bakushou jinsei gekijou → …gekijou 2           错（续作）
```

一条横线切不开 `caltron 6 in 1` 和 `castle quest`。所以方案 B（只调阈值）
注定要拿误伤换正确率 —— 实测提到 0.96 能消掉 94% 的错配，代价是有效匹配
掉一半。这就是为什么最后选 A。

### 23.3 实现

**`cover_art.py`** 新增一个纯函数（放在 `_raw_title` 之后）：

```python
_NUM_TOKEN = re.compile(r"\b(\d+|xii|xi|ix|viii|vii|vi|iv|iii|ii|v|x)\b")
_ROMAN = {"i": 1, "ii": 2, ..., "xii": 12}

def num_seq(name):
    """名字里的数字序列，罗马数字先转成数值。"""
    out = []
    for m in _NUM_TOKEN.finditer(str(name or "").lower()):
        tok = m.group(1)
        out.append(int(tok) if tok.isdigit() else _ROMAN.get(tok, 0))
    return out
```

效果：

| 输入 | 输出 | 说明 |
|---|---|---|
| `money game ii` | `[2]` | 罗马数字转数值 |
| `money game 2` | `[2]` | 和上面**同值**，所以不会被误杀 |
| `caltron 6 in 1` | `[6, 1]` | 多数字 |
| `family circuit '91` | `[91]` | 年份也是编号（这正合适） |
| `super mario bros` | `[]` | 无数字 |
| `rambo rev prg0` | `[]` | **紧贴字母的数字不算** —— rom 修订号不是游戏编号 |
| `megaman x` | `[10]` | `x` 是罗马数字 10 |

判据加在**两层**上，不只是模糊档：

1. **模糊档**（相似度那一层）：
   ```python
   if num_seq(n) != want_nums:
       continue
   score = SequenceMatcher(None, want, n).ratio()
   ```
2. **副标题前缀层**：libretro 也用 ` - ` 接编号，于是 `Family Quiz` 会匹到
   `Family Quiz - 4-nin wa Rival` —— 那是两款游戏，不是副标题。同样加一道。

> ⚠ 第 2 层是**端到端跑出来才发现漏的**。一开始只加在模糊档，探针跑完
> 以为干净了，真起服务抓图时 `family quiz` 还是贴到了续作上。

`pick_all()` 的副标题层也要加（轮播走的是这个函数）—— 三处共用一个
`num_seq`，不许各写一份。

`MIN_RATIO` 的值**一个数字没改**，只把注释改写了，写明「它拦不住续作，

### 23.10 教训

1. **相似度阈值不是万能旋钮。** 名字长度一过 6 个字符，续作就落进安全区。
   想靠调阈值解决，等于在错的和对的混在一起的区间里画一条线。
2. **结构判据（比数字）比连续量（比相似度）可靠。** 「数字序列必须一致」
   这十几行代码，比把阈值从 0.86 调到 0.96 的效果好得多，而且零误伤。
3. **探针跑绿不等于链路通。** 副标题层那条漏网，是端到端真抓图才发现的。
   桩测试覆盖不到「三层判据之间怎么互相放行」。
4. **回收站删除别信返回值。** `SHFileOperationW` 返回 2 也可能是成功，
   要解析 `$I` 元数据确认。
