# RetroMusic Lab 安卓移植可行性分析

> 分析日期：2026-10-19　基线版本：v4.18（17376 行 Python）
> 结论基于对现有代码的实际盘点，不是通用经验推断。

---

## 一、结论先行

**技术上可行，但这不是「移植」，是「重写一半」。**

- 真正卡人的不是解码库（libgme/miniaudio 都能编到 arm64），
  而是 **tkinter 在 Android 上根本不存在** + **Android 分区存储模型和这个软件的交互范式冲突**。
- 按现有功能 1:1 搬过去，工作量约 **4–6 周**，且手机上体验会明显变差。
- **但换一个产品定位，周期能压到 2–3 周，且体验更好**（见第五节）。

## 三、障碍分级

### 🔴 硬障碍（必须改，没有捷径）

| # | 障碍 | 现状 | 影响 |
|---|---|---|---|
| 1 | **tkinter 无 Android 运行时** | 8374 行 UI | Python-for-Android / Kivy **不支持 Tk**（Tk 依赖桌面窗口系统）。这 8374 行全部作废，必须用另一套 UI 重写 |
| 2 | **分区存储（Scoped Storage）** | `PickDialog` 目录树 + `os.scandir` 批量扫 | Android 10+ 不能随意遍历目录、不能任意写路径。改走 SAF 后，扫 1000 个文件从「毫秒级」变「几十秒到几分钟」。**这是产品体验降级，不是代码问题** |
| 3 | **7z 解压依赖 `tar.exe`** | `joshw_dl.py:197` 硬编码 `%SystemRoot%\System32\tar.exe` | Android 没有 bsdtar。要换 py7zr（纯 Python + pyppmd C 扩展，需自己写 recipe，慢 3–5 倍）或交叉编译 libarchive |
| 4 | **libgme 要交叉编译** | mingw 编的 `libgme.dll` + 4 个依赖 DLL | 需用 NDK 编 `arm64-v8a/libgme.so`。libgme 是老式 C++ Makefile，能编但要处理 STL/异常；`chip_decode.py` 里「禁调 identify_file（必段错误）」这条硬约束**必须在 arm64 上重新验证** |

### 🟡 中等障碍（有方案，需实测）

| # | 障碍 | 说明 |
|---|---|---|
| 5 | **miniaudio 无 Android wheel** | p4a 无官方 recipe。`miniaudio.h` 是单头文件且原生支持 AAudio/OpenSL ES，理论上可编，但要自己写 recipe。**这是最需要提前验证的一环**（试听功能全押在它上面） |
| 6 | **子进程解码** | `chip_decode.py` 每个 run 起子进程（因为 libgme 会卡死，必须隔离）。Android 上 fork 可用，但**内存翻倍** —— HES 256 轨场景在 4GB 手机上要设并发上限 |
| 7 | **后台下载** | 需 Foreground Service + 通知 + WakeLock，还要处理厂商 ROM 的后台查杀（国产 ROM 尤其激进） |
| 8 | **体积** | 现在 36.7MB exe → APK 预计 **60–120MB**（Python runtime + numpy + 库）。AAB base 上限 150MB，勉强够但很难看 |

### 🟢 几乎零改动

`chip_formats.py`（魔数表 + 时长推算）、`zh_titles.py`（1790 行中文名映射）、
`spc_wav.py`、`dl_convert.py` 的分轨/命名/磁盘门禁逻辑。
**这是最值钱的部分，而且是多年踩坑换来的**（比如 P1 四种格式的魔数公开规范都是错的）。

## 四、三条路线

| | **A. Kivy + python-for-android** | **B. 原生 Kotlin** | **C. Termux 过渡** |
|---|---|---|---|
| 逻辑复用 | ~80%（9000 行） | 0%（全部重写） | ~95% |
| UI 工作量 | 重写（Kivy DSL，控件生态弱） | 重写（体验最好） | 0 |
| 启动速度 | 慢（2–4s，Python 解释器冷启） | 快（<0.5s） | 慢 |
| 音频延迟 | 中 | 低（AAudio 直连） | 中 |
| 上架 Google Play | 中（体积/启动/64 位都过得了，但审核会问权限） | 高 | ❌ |
| 周期估算 | **4–6 周** | 8–12 周 | **1–2 天** |

**选 A 的理由**：54% 的代码（含所有踩过坑的格式识别）能活下来，这是这个项目最贵的东西。
**不选 B 的理由**：等于把 17376 行重写一遍，而且 chip_formats 里那些魔数/偏移结论要重新验证一遍 —— 那是几百小时的实测。

## 五、更重要的问题：该不该 1:1 搬

桌面版的价值是「**转换 + 烧卡**」：

- 大屏幕看 38,805 条曲库、键鼠批量勾选
- 写文件到 SD 卡给 sd2snes（MSU-1）
- x86 上算 HES 256 轨（很吃 CPU）

**手机上用户真正要的是「听」，不是「转」。**
没人会拿手机做一个 MSU-1 补丁包再插进烧录卡。转换功能搬到手机上，
既慢（手机 CPU）、又费电、又要处理 SAF 写入，投入产出比极低。

### 建议的产品形态

| 功能 | 桌面版 | 安卓版（建议） |
|---|---|---|
| 曲库浏览（38,805 条 + 中文名） | ✅ | ✅ 保留 |
| 芯片音乐播放（10 种，libgme） | ✅ | ✅ 保留（核心） |
| 在线试听 / 下载管理 | ✅ | ⚠ 可选（砍掉 7z 依赖就砍掉了最大的坑） |
| SPC/NSF → WAV 转换 | ✅ | ❌ 砍 |
| BIN+CUE / MSU-1 打包 | ✅ | ❌ 砍 |
| 下载窗（三列 + 试听） | ✅ | ❌ 砍 |

砍完之后，剩下的障碍只有 **#1（UI 重写）+ #4（libgme 编译）+ #5（miniaudio）**，
7z / 分区存储 / 后台服务 / 体积全部消失。周期 **2–3 周**。

> 顺带一提：真要转换，手机上更合理的是"导出到 PC 队列"——手机负责挑歌，
> 生成一个清单（.txt/JSON），用户在 PC 上跑桌面版批量转。零风险，且不牺牲任何体验。

## 七、立刻值得做的验证（1 小时）

**在 Termux 里做，不写一行 UI**：

```bash
pkg install python clang cmake ninja
# 编 libgme（远端仓库 ares-emulator/libgme 或 blargg/game-music-emu）
# 得到 libgme.so → 改 chip_decode.py 的库名探测
python msu1_to_cd.py --selftest vendor/sample.spc
```

这一步能一次性排掉 3 个最大的不确定性：

1. libgme 能否在 aarch64/Android bionic 上编过
2. `gme_track_info` 的 ctypes 调用约定在 arm64 上是否一致（桌面版踩过二级指针的坑）
3. PCM 输出是否逐字节一致（端序、对齐、浮点）

**如果这一步失败，说明路线 A 的底座不稳，要重新评估。**
如果成功，后面就是纯 UI 工程活，风险可控。

## 八、风险清单

| 风险 | 概率 | 缓解 |
|---|---|---|
| miniaudio 编不到 Android | 中 | 退路：播放改用 libgme 直接吐 PCM + `pygame.mixer`/`simpleaudio`，或 JNI 调 AudioTrack |
| libgme 在 bionic 上行为差异 | 中 | 用 `vendor/sample.spc` 做 sha 比对门禁，跟桌面版对齐 |
| SAF 遍历太慢导致下载管理不可用 | 高 | 改存 App 私有目录（`getExternalFilesDir`），用户要导出再走 SAF |
| 国产 ROM 杀后台导致下载中断 | 高 | 前台服务 + 断点续传（`dl_convert.py` 已有 manifest 记账，可复用） |
| APK 超过 100MB 影响安装转化 | 中 | 索引按机种拆成 Play Asset Delivery 或首次启动下载 |
| 维护成本翻倍（两套 UI 同步） | **高** | **UI 不共享，但逻辑层单源**：逻辑层改动必须两边跑回归 |

---

## 九、一句话总结

> 底座是好的（逻辑层干净、52% 可复用），但 UI 层 100% 重写不可避免。
> **别做"手机上的转换器"，做"手机上的芯片音乐播放器"** —— 同一批代码，
> 周期从 4–6 周降到 2–3 周，体验反而更好。
